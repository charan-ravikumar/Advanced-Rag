1. ONE-PARAGRAPH PITCH (say this out loud in the interview)
--------------------------------------------------------------------------------
I built a RAG (retrieval-augmented generation) pipeline for question answering
over scientific papers (QASPER dataset). Instead of just wiring up a vector DB,
I treated it as an experiment: I compared chunking strategies (recursive,
layout, semantic) and retrieval configurations (vector-only, vector+BM25,
hybrid+RRF fusion, +cross-encoder reranker) with a checkpointed evaluation
harness. Later I audited my own project, found that several headline numbers
were not backed by raw data and a few features were buggy, and started fixing
them. The key message: I measure, I question my own claims, and I fix them.

3. WHY I MADE THE KEY DESIGN CHOICES  (interview "why" answers)
--------------------------------------------------------------------------------
* Hybrid (BM25 + vector) instead of vector only
    Why: scientific text has exact terms (model names, metrics, acronyms) that
    dense embeddings blur; BM25 catches exact matches, vectors catch meaning.
* RRF (Reciprocal Rank Fusion, k=60) instead of score blending
    Why: BM25 scores and cosine similarities are on different scales; RRF only
    uses ranks, so no score normalization or tuning is needed. Weighted RRF
    lets me bias toward one retriever. Unit-tested in tests/unit/test_fusion.py.
* Semantic chunking vs recursive
    Why: I hypothesized that splitting on meaning boundaries keeps answers
    intact. Result: small gain, NOT statistically significant (see Section 4).
* Cross-encoder reranker kept OPTIONAL / off by default on CPU
    Why: tiny recall gain (+1pp) for a huge latency cost on CPU. A GPU would
    change this decision. This is a legit cost/benefit engineering call.
* Redis fails open
    Why: cache is an optimization; if Redis is down the API must still answer.
* Per-call overrides (retrieval_mode_override, use_rrf_override,
  reranker_override)
    Why: lets me A/B different pipeline configs without redeploying.
* Per-question checkpoint files (evaluation/checkpoints/*.jsonl)
    Why: long LLM-judged evals crash/rate-limit; checkpoints make them
    resumable AND let me compute paired statistics later (bootstrap CIs).

4. WHAT THE DATA ACTUALLY SHOWS (honest numbers - use these, not the README)
--------------------------------------------------------------------------------
Dataset: QASPER dev subset (200 papers, 100 questions). Small -> wide CIs.

Retrieval ablation (semantic chunking), measured:
  Vector only            Recall@5 0.21   MRR 0.157
  Hybrid (no RRF)        Recall@5 0.21   MRR 0.157   (identical -> suspicious/bug)
  Hybrid + RRF           Recall@5 0.27   MRR 0.175
  Production (+rerank)   Recall@5 0.28   MRR 0.170

Defensible claim:
  Hybrid+RRF improves Recall@5 from 0.21 to 0.27 = +6 percentage points
  (+28.6% relative). Paired bootstrap: 6 wins / 0 losses, 95% CI [+2, +11] pp.

Chunking comparison (Recall@5): recursive 0.25, layout 0.26, semantic 0.28.
  Paired test semantic vs recursive: 8 wins / 5 losses, CI [-4, +10] pp
  -> NOT distinguishable. Say "directionally better, not significant".

Retrieval latency: measured P50 ~0.5 s, P95 ~1.0-1.3 s.
End-to-end (retrieval+LLM) is much larger and noisy (LLM-dominated).
Reranker on CPU: ~3 s (checkpoint median) to ~11.7 s (one noisy run).

5. KNOWN PROBLEMS I FOUND IN MY OWN PROJECT (own them in the interview)
--------------------------------------------------------------------------------
Claims that were wrong / unsupported (README + resume_bullets_v2.md):
  - "+44% Recall@5": baseline 0.188 was ESTIMATED by a formula in
    eval/feature_contrib.py, never measured. Real: +28.6% (0.21 -> 0.27).
  - "P50 latency 1.7 s": that was mean end-to-end latency, not P50 retrieval.
  - "CrossEncoder +12.6 s": a difference of two noisy means, wrong model named
    (benchmark used bge-reranker-base, docs said ms-marco-MiniLM).
  - "SSE streaming": it is plain-text StreamingResponse, not text/event-stream.
  - "Throughput 4.2/14.3 QPM": computed as 60/latency for one sequential
    stream - that is latency inverted, not capacity.
  - "0% error rate": hard-coded literal, not measured.
  - "Two-tier cache": really two different caches (query-embedding LRU and
    Redis for final answers), not tiers.
  - Grafana/Phoenix mentioned but no dashboards/configs exist.

Real bugs (from technical_audit/03_CODE_REVIEW.md):
  - Gemini fallback broken: config={"timeout": 30} raises ValidationError on
    google-genai, so fallback always fails.
  - Failed LLM results can be cached.
  - Fusion output not truncated before reranking (unbounded rerank input).
  - Chunker can drop leftover small groups of text (data loss).
  - Three chunking strategies mixed in one Chroma collection.
  - BM25 is in-memory and ignores metadata filters.
Gaps: no auth/rate limit, no Dockerfile/CI/.env.example, polluted
requirements.txt, thin tests (none for cache/API/context builder).

HOW TO TALK ABOUT THIS: "I audited my own work, found my headline number was
derived rather than measured, and replaced it with a paired-bootstrap result.
That is the number I defend." Interviewers value this far more than a big
number they can poke holes in.

9. LIKELY INTERVIEW QUESTIONS - QUICK ANSWERS
--------------------------------------------------------------------------------
Q: Why hybrid retrieval?
A: Dense embeddings capture semantics but miss exact tokens (acronyms, model
   names); BM25 does the opposite. Fusing them gave +6pp Recall@5 on my
   eval, 6 wins / 0 losses on paired questions.

Q: Why RRF instead of weighted score sum?
A: Scores from BM25 and cosine are not comparable. RRF uses ranks only, is
   parameter-light (k=60), robust, and easy to test.

Q: Is semantic chunking better?
A: Directionally (0.28 vs 0.25 Recall@5) but the paired CI spans zero
   [-4, +10] pp, so I cannot claim it on 100 questions.

Q: Why isn't the reranker on by default?
A: +1pp recall for seconds of CPU latency (and it lowered faithfulness in one
   run). On a GPU I would re-evaluate. Decision driven by measured cost/benefit.

Q: What would you fix first / what is wrong with the project?
A: Evidence integrity (a derived baseline presented as measured), the broken
   Gemini fallback, error caching, unbounded rerank input, and chunker data
   loss. I've documented them and have a prioritized plan (Section 6).

Q: How would this scale?
A: Replace in-memory BM25 with persistent FTS5/OpenSearch, incremental
   ingestion with deterministic IDs, async endpoints, LLM gateway with retries
   and circuit breaker, load-test to find the Chroma Cloud concurrency
   ceiling (~10 concurrent reads), then scale horizontally behind a queue.

Q: How do you evaluate RAG quality?
A: Retrieval: Recall@k, MRR against gold evidence; generation: faithfulness
   and answer relevance via LLM judge (noisy - needs calibration); always
   report confidence intervals and use paired comparisons.

Q: Biggest lesson?
A: Numbers are only valuable if traceable to raw data. I now label each
   metric precisely (retrieval P50 vs end-to-end P50) and cite its source file.
