### Evidence discipline: claims log and code fingerprint
- **What we did:** Added `docs/CLAIMS_LOG.md` (metric, value, run folder, code fingerprint), `utils/fingerprint.py` (sha256 over all `.py`/`.yaml` files sorted by path, CRLF-normalised, caches/venvs excluded) and standing rules in `CLAUDE.md`. Stripped every performance number from `README.md` (replaced with "TBD: see CLAIMS_LOG"). A snapshot of the original project is at `Advanced-Rag-main__v1_snapshot`.
- **Why (the problem it solves):** The original project published numbers that did not trace to raw data — an estimated baseline was presented as measured. That is the fastest way to lose credibility in an interview: one probing question ("show me the run") collapses every other claim. Now a number can only be published if it has a saved run artifact and the exact code version that produced it.
- **Alternatives considered and why rejected:** (1) Git SHA — the project is not under git; the fingerprint gives the same "which code produced this" guarantee without it. (2) Just being careful — relies on discipline, leaves no audit trail. (3) Experiment trackers (MLflow/W&B) — heavier, may involve external services; a markdown table plus run folders is enough at this scale.
- **Trade-offs / what it costs:** Every published number needs a run and a log row, so README updates are slower. The fingerprint covers only `.py`/`.yaml`, so changes to data files, `.env`, or dependency versions are not captured (record those in the run folder). Hashing includes file paths, so renames change it, intentionally.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_fingerprint.py` (determinism, content/rename sensitivity, yaml inclusion, exclusions, line-ending normalisation, order independence). README numbers removed are listed in the task report; the pre-edit README is preserved in the snapshot folder.
- **Likely interview questions and strong answers:**
  - *"How do you make sure your reported numbers are real?"* — "Every number in my README must have a row in a claims log pointing to a saved run folder and a code fingerprint, a sha256 of all source and config files. If I can't regenerate or open the artifact, the number doesn't get published. I learned this the hard way: an earlier version of this project showed a baseline that was an estimate, not a measurement, so I removed all numbers and re-derived them from real runs."
  - *"Why not a git SHA?"* — "This project wasn't under version control; the content hash identifies the exact code state without it, and still works if I add git later."
  - *"What does the fingerprint not cover?"* — "Data, model weights, dependency versions and env vars; those are recorded alongside the run artifacts."
- **Honest limitations:** The claims log is a convention, not enforced by tooling (no CI check yet that README numbers appear in the log). The fingerprint is computed at log time; if code changes after a run but before the fingerprint is taken, they can mismatch — compute it at the start of the run and store it in the run folder.

### Establish a known test baseline before refactoring
- **What we did:** Ran the whole suite in the new venv without fixing anything or faking credentials, and recorded every test with a result and a failure category in `docs/TEST_BASELINE.md`. Result: 16 passed, 37 failed; all 37 fail at import time (HF model load in `rag/chunkers.py:69` and `rag/embeddings.py:19`; Chroma Cloud connection in `db/vectordb.py:25,42`). Listed the import-time side-effect lines to remove next.
- **Why (the problem it solves):** Without a baseline you cannot tell regressions you introduced from failures that already existed, and a red suite teaches everyone to ignore tests.
- **Alternatives considered and why rejected:** Fixing tests while running them for the first time (mixes cause and effect, and hides what was broken originally). Setting dummy credentials to get green (would mask the real design problem: importing a module opens network connections).
- **Trade-offs / what it costs:** A red baseline is uncomfortable and delays visible progress. Because the failures are import-time, the test bodies never executed, so wrong tests and genuine bugs are still unknown; the baseline must be redone after the import side effects are removed.
- **Evidence it works (test or measurement, with file path):** `docs/TEST_BASELINE.md`; environment in `docs/env_baseline.txt`.
- **Likely interview questions and strong answers:**
  - *"How do you safely refactor code that has weak tests?"* — "First characterise current behaviour: record what passes and fails today and why, and add tests that pin down what the code actually does. Then change it in small steps with that suite as the safety net, re-running after each step, so any new red is attributable to the last change."
  - *"Why didn't you just set fake env vars to make tests pass?"* — "That hides the real defect. Importing a module should not connect to a database; the fix is to remove the side effect, not to feed it dummy values."
- **Honest limitations:** 37 of 53 tests are uninformative until imports are made side-effect free. While establishing the baseline, the test run imported `db/vectordb.py` with the real `.env`, which connected to Chroma Cloud once (a `get_or_create_collection`, not a delete). That broke the "never touch Chroma Cloud" rule and is why CLAUDE.md rule 10 was added.

### Reproducible environment outside synced folders
- **What we did:** Created a virtualenv at `%LOCALAPPDATA%\advrag\venv` (not under OneDrive), installed the needed packages only through the configured package index, and saved exact versions with `pip freeze` to `docs/env_baseline.txt`. Did not rewrite `requirements.txt` yet.
- **Why (the problem it solves):** A virtualenv or SQLite-backed store inside OneDrive causes sync churn (thousands of small files) and file-lock problems. An environment that can be rebuilt from a recorded list of versions is what makes results reproducible.
- **Alternatives considered and why rejected:** Venv inside the project folder (synced by OneDrive). Reusing the global Python (unrecorded, shared state). Installing straight from the existing `requirements.txt` (it is a polluted `pip freeze`, see below).
- **Trade-offs / what it costs:** The environment lives away from the code, so the path must be documented (CLAUDE.md). I installed unpinned latest versions of the packages the code needs, so they differ from the pins in `requirements.txt` (for example `openai` resolved to a version above the `<2.0` bound in `pyproject.toml`).
- **Evidence it works (test or measurement, with file path):** `docs/env_baseline.txt`; the suite runs in this venv (`docs/TEST_BASELINE.md`).
- **Likely interview questions and strong answers:**
  - *"How do you make sure someone else can reproduce your results?"* — "Pinned versions recorded from the environment that produced the run, a code fingerprint, and saved run artifacts. The environment is rebuildable from the list rather than from memory."
- **Honest limitations:** The freeze records versions but not hashes or the OS/Python build; `requirements.txt` and `pyproject.toml` still disagree and need reconciling. The embedding model is not yet in the local cache, so a fully offline rebuild is not yet possible.

### Stale documentation is a liability
- **What we did:** Scanned README, `resume_bullets_v2.md`, `PROJECT_CONTEXT.txt`, `docs/`, `eval/results/` and `technical_audit/` for performance numbers and claims (percentages, latencies, QPM, SSE, FAISS, spaCy, Grafana, Phoenix, two-tier cache, cache-hit times). Indexed every hit by file:line in `docs/STALE_CLAIMS_INDEX.md` and put the banner "UNVERIFIED: written before the rebuild. Do not quote. See docs/CLAIMS_LOG.md." at the top of each markdown/text file. Content was not deleted or rewritten. Also found that `scripts/run_evaluation.py` rewrites README.md (and `benchmark_summary.md`), so it is banned in CLAUDE.md.
- **Why (the problem it solves):** Docs that describe a system that no longer exists, or numbers nobody can trace, are worse than no docs because a reader will trust them.
- **Alternatives considered and why rejected:** Deleting the old docs (loses history and the record of what was claimed). Silently editing the numbers (that is how untraceable numbers got in originally). Leaving them as they are (readers will quote them).
- **Trade-offs / what it costs:** Banners make the repository look messy until each file is rewritten from verified runs. The CSV result files could not take a banner without breaking them; they are listed in the index only.
- **Evidence it works (test or measurement, with file path):** `docs/STALE_CLAIMS_INDEX.md` (hit counts per file).
- **Likely interview questions and strong answers:**
  - *"What do you do with documentation that no longer matches the code?"* — "Mark it as unverified immediately, keep it for history, and rebuild it from measured results; a wrong doc that looks authoritative is a liability."
- **Honest limitations:** The scan is keyword-based, so it can miss prose claims with no numbers, and it includes some false positives such as version numbers.

### Deterministic chunk IDs plus content hashes
- **What we did:** Defined a frozen `Chunk` contract in `rag/schemas_ingest.py`. `chunk_id = sha1(doc_id|strategy|chunk_idx|text_hash)[:16]`, `text_hash = sha256(text)`, `doc_version = sha256(full document text)`. The old pipeline used `uuid4()` per chunk.
- **Why (the problem it solves):** With uuid4, every re-ingest created a new copy of every chunk (duplicates in the index) and no two runs were comparable. Deterministic ids make upsert idempotent (same input, same ids, no duplicates), and `doc_version` lets ingestion skip unchanged documents and replace only changed ones.
- **Alternatives considered and why rejected:** Wipe-and-rebuild on every run: costs full re-embedding time, leaves the index empty or inconsistent while it runs, and one bad run destroys data. Content-only ids (hash of text alone): identical text in two papers or two strategies would collide.
- **Trade-offs / what it costs:** Any text edit changes that chunk's id (old ids must be deleted: delete-by-doc then upsert). With whole-document chunkers (recursive, semantic), an edit can also shift boundaries and change neighbouring chunk ids, so updates are per document, not per chunk.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_chunk_contract.py` (determinism for all three strategies, different strategies give disjoint ids, one-character edit changes only the edited section's chunk id and the doc_version for layout).
- **Likely interview questions and strong answers:**
  - *"How do you re-index when a document changes?"* — "Each chunk id is derived from content and position, and each document carries a version hash. On ingest I compare the stored version with the new one: same, skip; different, delete that document's chunks and upsert the new ones. Nothing is ever wiped wholesale, and re-running is safe."
- **Honest limitations:** The ids are only as stable as the chunker: a change to chunking parameters changes every id (intended, since the content changed). `doc_version` hashes text only, not the chunking config, so a config change needs an explicit re-ingest (the manifest records the config).

### doc_id and character offsets in chunk metadata
- **What we did:** Every chunk carries `doc_id` (always the Qasper paper_id, never the title), its section, `char_start`/`char_end` into the section text and its order in the document. The adapter in `rag/chunk_adapter.py` derives offsets by locating each chunk's text in the source.
- **Why (the problem it solves):** Relevance used to be judged with fuzzy lexical overlap, which is both lenient and unfalsifiable. With doc_id and offsets, relevance can be defined by document or by character span, context building can fetch neighbouring chunks, and citations can point at exact text.
- **Alternatives considered and why rejected:** Title as the document key (titles can collide or change). Overlap-score relevance (ambiguous threshold, hides errors).
- **Trade-offs / what it costs:** Extra metadata per chunk, and an adapter step, because the chunkers do not report offsets themselves.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_chunk_contract.py::test_offsets_round_trip_modulo_whitespace`; confidence counts for the first 20 papers are in the Gate 1 report (not published as a claim).
- **Likely interview questions and strong answers:**
  - *"How do you know a retrieved chunk is correct?"* — "Each chunk has a document id and a character span in a known section, so I can check it against the gold evidence span or document id instead of guessing from word overlap, and I can show the exact quote in the answer."
- **Honest limitations:** Chunks that cross a section boundary (recursive and semantic chunk the whole document text) are clipped to the section where they start and flagged `spans_sections` in the adapter side channel, so their offsets cover only part of the chunk. In the first 20 papers this affects 55 of 748 recursive chunks and 140 of 317 semantic chunks (HashEmbedder grouping).

### Never silently guess offsets
- **What we did:** The adapter labels every chunk's offset as `exact`, `normalised` (found only after collapsing whitespace), `ambiguous` (more than one candidate position at or after the cursor) or `not_found` (offsets set to -1). The label lives in a side channel, not in the vector store metadata.
- **Why (the problem it solves):** A wrong offset gives a wrong citation or a wrong relevance label that looks perfectly right. An explicit class makes the weakness measurable and lets ingestion report it.
- **Alternatives considered and why rejected:** Always take the first match (silent errors for repeated text). Raise on any mismatch (would block ingestion for harmless whitespace differences).
- **Trade-offs / what it costs:** Extra bookkeeping, and consumers must handle -1 offsets.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_chunk_contract.py::test_locate_whitespace_tolerant_and_labels`.
- **Likely interview questions and strong answers:**
  - *"What if the same sentence appears twice?"* — "The locator searches forward from the previous chunk's position and flags the result ambiguous if more than one candidate remains, rather than silently picking one."
- **Honest limitations:** The first 20 papers contained no ambiguous or not_found chunks, which shows the class works on real data but is not proof for the full corpus; repeated boilerplate paragraphs elsewhere could produce ambiguous cases.

### Property-based tests for the chunker
- **What we did:** Wrote hypothesis tests (`tests/unit/test_chunker_properties.py`) that generate papers (short, long, unicode, repeated paragraphs) and assert, for every strategy: no content lost (every non-whitespace character of every section lies inside some chunk), no empty chunks, determinism, a character cap and a token cap. They were written and run BEFORE touching the chunkers.
- **Why (the problem it solves):** Example-based tests passed while the semantic chunker silently dropped text. The tests found it on the first run.
- **Alternatives considered and why rejected:** More hand-written examples (they only cover cases I already thought of); eyeballing output on a few papers.
- **Trade-offs / what it costs:** Slower suite (about 3 minutes), and a few failures were test-side artefacts (the offset locator mis-placing repeated text) that had to be separated from real bugs.
- **Evidence it works (test or measurement, with file path):** Before the fix 8 property tests failed; minimal reproduction `test_minimal_semantic_drops_small_leading_group` (`"Tiny intro."` plus a ~1,995-character paragraph: the small group was reset and dropped when `temp + group` exceeded the cap). After the fix all property tests pass (`tests/unit/test_chunker_properties.py`).
- **Likely interview questions and strong answers:**
  - *"How did you find the dropped-content bug?"* — "A coverage property: every non-whitespace character of every section must be inside a chunk. Hypothesis shrank the failure to two paragraphs."
  - *"How do you safely refactor code with weak tests?"* — "Write properties that characterise what must stay true, watch them fail on the old code, then fix in small steps."
- **Honest limitations:** The main property runs use a HashEmbedder and a counter estimate, not the real model; the `model`-marked tests (`test_real_tokenizer_token_cap`, `test_fallback_counter_is_safe_under_real_tokenizer`) check the real tokenizer and run when the pinned model is cached.

### Chunk size must fit the embedding model window
- **What we did:** Chunks are capped by characters (2000) AND by tokens (`min(chunking.max_tokens, embedder.max_seq_length)` = 256). Oversized pieces are re-split at sentence, then word, then character boundaries (`rag/tokens.py`). Caps and sizes moved from literals into `config.yaml`.
- **Why (the problem it solves):** all-MiniLM-L6-v2 silently truncates input beyond its window (256 tokens here). A 2000-character chunk is often more than that, so the tail of the chunk was never embedded: it was stored but unfindable. The old layout chunker emitted whole sections of any size.
- **Alternatives considered and why rejected:** An embedder with a longer window (not now: changes the model variable under evaluation and needs a download); only a character cap (does not bound tokens).
- **Trade-offs / what it costs:** More, smaller chunks for long sections; a re-split can cut mid-sentence only when a single sentence exceeds the window.
- **Evidence it works (test or measurement, with file path):** `test_token_cap` and `test_char_cap` for all strategies; minimal case `test_minimal_layout_chunk_exceeds_embedding_window`.
- **Likely interview questions and strong answers:**
  - *"What is max_seq_length and why does chunk size matter?"* — "It is how many tokens the encoder reads; the rest is dropped without error. So a chunk must fit or part of it is invisible to search."
- **Honest limitations:** The cap was verified with a regex counter; the real WordPiece check is skipped until the model is cached. Special tokens are accounted for (+2) only when the embedder exposes a tokenizer.

- **What we did:** Declared the chunking comparisons from the original project void and recorded none of the offset-confidence numbers as claims.
- **Why (the problem it solves):** The old chunkers dropped content, exceeded the embedding window and (for recursive and semantic) crossed section boundaries, and their doc ids were random. Any "strategy A beats B" result measured those defects as much as the strategies.
- **Alternatives considered and why rejected:** Keep the old numbers with a caveat (a reader will quote the number, not the caveat).
- **Trade-offs / what it costs:** The headline result has to be re-earned.
- **Evidence it works (test or measurement, with file path):** The defects are pinned by `tests/unit/test_chunker_properties.py`. The unmodified v1 semantic chunker (read from the snapshot) was run on the first 20 corpus papers: with the real MiniLM embedder 127 of 404 chunks (31.4%) crossed a section boundary; with HashEmbedder 140 of 317 (44.2%). The earlier 44% was therefore a HashEmbedder artefact: the real model gives fewer, because it groups differently. ### Chunking per section and the doc_id bug
- **What we did:** All three strategies now chunk within one section only (`section_pos` in chunk metadata). Undersized chunks (`chunking.min_chunk_chars`) merge only within their section. Chunkers report each chunk's section-relative start, which the adapter verifies instead of guessing. `spans_sections` is False for every strategy, enforced by `test_never_spans_sections` and `test_undersized_chunks_not_merged_across_sections`. doc_id is the corpus paper id.
- **Why (the problem it solves):** A chunk crossing sections carries the wrong section label and clipped offsets. Separately, the old converter did `paper.get("id", uuid4())`; corpus entries have no `id` field, so every ingest assigned random document ids, which made document-level evaluation impossible and re-ingestion non-idempotent.
- **Alternatives considered and why rejected:** Keep whole-document chunking and clip offsets (labels stay wrong); infer doc_id from the title (titles are not unique).
- **Trade-offs / what it costs:** Context cannot flow across section headings, so very short sections give short chunks; paragraph-level continuity is lost at boundaries.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_chunker_properties.py`, `tests/unit/test_chunk_contract.py::test_doc_id_is_paper_id_not_title`.
- **Likely interview questions and strong answers:**
  - *"Why chunk per section?"* — "So every chunk has one true section label and exact offsets, which citation and evaluation need."
  - *"What was the doc_id bug?"* — "A uuid4 fallback assigned random ids on each ingest, so I could not map retrieved chunks to gold papers."
- **Honest limitations:** Section boundaries come from the dataset's parsing. Also, a bug found on the way: Langchain's `start_index` is wrong for repeated text, so the chunker now computes positions itself.

### Import-safe stores and embedders, with a hermetic test guard
- **What we did:** Removed every import-time side effect from `db/vectordb.py`, `rag/embeddings.py`, `rag/context_builder.py` and the chunkers: the embedding model, the Chroma client, `.env` loading and the tiktoken vocabulary are all created lazily. `db.vectordb` now refuses every cloud call (including `clear_collection`) unless `ADVRAG_ALLOW_CLOUD=1`. `tests/conftest.py` makes every test hermetic: HuggingFace offline, non-loopback sockets and DNS refused, `chromadb.CloudClient` replaced by a function that raises. `tests/unit/test_import_guard.py` imports each module in a subprocess whose network, `CloudClient` and `SentenceTransformer.__init__` are poisoned. New `db/store.py` (`VectorStore` protocol, `ChromaStore`, `build_store`) opens a local `PersistentClient` under `%LOCALAPPDATA%/advrag/chroma`, one collection per strategy, with no "clear collection" method. `rag/embedders.py` gained the `Embedder` protocol and `SentenceTransformerEmbedder` (lazy, `local_files_only`).
- **Why (the problem it solves):** Importing `db.vectordb` connected to Chroma Cloud with real credentials and loading `rag.embeddings` loaded a model. During the test baseline that sent one real request to the cloud from a test run. A test suite must be unable to do that, not merely avoid it by habit.
- **Alternatives considered and why rejected:** A "please don't" rule in CLAUDE.md (already broken once); mocking only inside individual tests (a new test can forget to); a Docker sandbox (heavy for a laptop project).
- **Trade-offs / what it costs:** Dependency injection (embedder, store passed in) instead of globals; `rag/retrieval.py` still has import-time side effects (LLM clients, BM25 build) and is deliberately untouched until its own refactor, so `test_fusion.py` and `test_retrieval.py` stay out of the suite for now.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_import_guard.py` (module imports, no state left behind, cloud calls refused, guard blocks sockets/DNS/CloudClient) and `tests/unit/test_store.py`.
- **Likely interview questions and strong answers:**
  - *"How do you stop tests from hitting production services?"* — "Fail closed: the test harness blocks outbound sockets and poisons the cloud client, and an import test proves the library modules do nothing at import."
  - *"Why inject the embedder and store?"* — "So ingestion and chunking run in tests with a deterministic hash embedder and a temp-dir Chroma, with no network."
- **Honest limitations:** The socket guard covers Python-level connections only; a native extension opening its own socket would bypass it.

### Pinned embedding model, real tokenizer as the source of truth
- **What we did:** Downloaded `sentence-transformers/all-MiniLM-L6-v2` once, with the owner's approval, at revision `1110a243fdf4706b3f48f1d95db1a4f5529b4d41` (only the files needed for inference). The revision lives in `config.yaml` and `docs/env_baseline.txt`; the embedder loads from the local cache only and raises a clear error instead of downloading. Chunkers count tokens with the embedder's own tokenizer (`count_tokens`, including [CLS]/[SEP]).
- **Why (the problem it solves):** An unpinned model name means the vectors can change under you, so two runs are not comparable. Counting tokens with a regex undercounts WordPiece, so chunks that looked within the window were truncated at embed time.
- **Alternatives considered and why rejected:** A safety multiplier on the regex counter (cannot cover CJK or chemical names, which ran at 4-5x the regex count in a probe); relying on the model's silent truncation.
- **Trade-offs / what it costs:** Chunking with the real tokenizer is slower and needs the model cached. A conservative estimator (`estimate_token_count`) is kept only as the no-tokenizer fallback for tests.
- **Evidence it works (test or measurement, with file path):** On the first 20 papers, chunks built with the OLD regex counter reached 357 real tokens, with 22 of 748 recursive, 246 of 532 layout and 213 of 620 semantic chunks over 256. With the real embedder, 0 chunks exceed 256 in all three strategies, and the estimator fallback also gives 0 over 256 (max 231). Saved in `runs/measurements/chunk_coverage_20261121T090107Z/results.json` (key `token_counters_first_20`; fingerprint `8378f805…2842`; logged in `docs/CLAIMS_LOG.md`). Correction: an earlier version of this entry cited `chunking_20261121T075552Z` for the regex-counter figures, but that file's "fallback" section holds the estimator result; the regex figures were console-only until they were re-measured and saved in the artifact above (identical numbers). Tests: `tests/unit/test_chunker_properties.py::test_real_tokenizer_token_cap` and `::test_fallback_counter_is_safe_under_real_tokenizer` (marked `model`).
- **Likely interview questions and strong answers:**
  - *"How do you know your chunks fit the model?"* — "I count with the model's own tokenizer, test it independently with the raw tokenizer, and ingestion re-verifies every stored chunk."
  - *"Why pin a revision?"* — "A model name resolves to whatever the hub serves today; the commit hash makes the embedding space reproducible."
- **Honest limitations:** The estimator fallback undercounts heavily accented and CJK text (a stress paragraph reached 293 real tokens); it is test-only, which is why production passes the real embedder. The 20-paper sample is small.

### Local Chroma for dev and eval, Cloud only as a deploy target
- **What we did:** All development, ingestion and evaluation use a local `chromadb.PersistentClient` under `%LOCALAPPDATA%/advrag/chroma` (override: `CHROMA_LOCAL_PATH`; OneDrive paths are refused), opened by `db.store.build_store(cfg, strategy)`, one collection per chunking strategy. The Chroma Cloud code in `db/vectordb.py` is kept only as a legacy deploy path and refuses every call unless `ADVRAG_ALLOW_CLOUD=1`.
- **Why (the problem it solves):** Experiments need to be repeatable, free, offline and destructible-by-mistake-safe. A shared cloud database fails all four: another run (or a stray `clear_collection()`) changes your data, results depend on network and quota, and the "known state" of the corpus is unknowable.
- **Alternatives considered and why rejected:** Develop against the cloud collection (what v1 did; one script wiped it on every run); an in-memory client (no persistence between ingest and eval runs); a throwaway server in Docker (extra moving part with no benefit for a single-user project).
- **Trade-offs / what it costs:** Local results do not prove the deployed service behaves the same (same Chroma engine, but not the same network, auth or scale), so a deploy step needs its own smoke test. SQLite-backed files must live outside synced folders.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_store.py` (path override, precedence, OneDrive refusal) and `tests/unit/test_import_guard.py::test_cloud_access_refused_without_opt_in`.
- **Likely interview questions and strong answers:**
  - *"Why not just use the cloud database for development?"* — "Because I could not tell what state it was in or reproduce a run. Locally, a run is a directory I can recreate from a manifest, and no test or script can damage shared data."
  - *"How does the code switch between local and cloud?"* — "Behind a `VectorStore` protocol; the local implementation is the default and the cloud one is opt-in by an environment variable."
- **Honest limitations:** Only the local implementation exists and is tested; the cloud implementation is legacy code that is no longer exercised.

### Dependency injection instead of import-time clients
- **What we did:** Anything that talks to something external or heavy is passed in: chunkers and ingestion take an `Embedder` (`rag/embedders.py`), ingestion takes a `VectorStore` (`db/store.py`), and `build_store(cfg, strategy, client=...)` accepts a ready client. Modules create nothing at import time. `rag/retrieval.py` is the remaining exception and is marked with a TODO listing its eight import-time side effects.
- **Why (the problem it solves):** `rag/retrieval.py` built LLM clients, loaded the entire corpus from the cloud and indexed BM25 at import, so it could not even be imported without credentials and network; its tests were red by construction (37 of 53 tests failed at baseline).
- **Alternatives considered and why rejected:** Patching module globals with `unittest.mock` inside each test (fragile, order-dependent, and the import itself had already hit the network); a dependency-injection framework (too heavy for this size).
- **Trade-offs / what it costs:** More parameters to pass around and a constructor to wire up at the entry points. A small `Embedder` protocol must stay narrow, or fakes become hard to write.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_ingestion.py` runs the whole ingest pipeline with a `HashEmbedder` and a temp-dir Chroma, with no network and no model; `tests/unit/test_chunkers.py` injects `HashEmbedder` into the semantic chunker.
- **Likely interview questions and strong answers:**
  - *"How do you test code that depends on external services?"* — "I inject the dependency behind a small interface, so the test passes a deterministic fake (a hash embedder, a temp-dir vector store) and the code under test is the real code. I keep a few opt-in tests against the real service, and I make sure the default suite cannot reach it."
  - *"Mocks or fakes?"* — "Fakes for things with behaviour (a store that really stores), mocks only to assert a call did or did not happen, for example that a second ingest made no upsert."
- **Honest limitations:** A fake can drift from the real service; the `model`-marked tests and the real ingest run are the check on that. Retrieval has not been converted yet.

### Tests must be structurally unable to reach production services
- **What we did:** `tests/conftest.py` applies an autouse guard to every test: HuggingFace offline, non-loopback sockets and DNS lookups raise `NetworkBlockedError`, `chromadb.CloudClient` is replaced by a function that raises, and `ADVRAG_ALLOW_CLOUD` is removed. `tests/unit/test_import_guard.py` imports every library module in a subprocess with the same things poisoned. Modules that cannot yet be imported safely (`rag/retrieval.py`) are skipped with a visible reason instead of being imported.

- **Alternatives considered and why rejected:** "Be careful" and a CLAUDE.md rule (already failed once); removing the credentials from `.env` (still breaks the moment someone adds them back); a separate network namespace or container (heavy on a laptop).

- **Likely interview questions and strong answers:**
  - *"How do you prevent tests from touching production?"* — "Fail closed in the harness: outbound sockets and the production client are blocked for every test, and an import test proves library modules do nothing at import. - **Honest limitations:** The guard covers Python sockets only. The incident was one read-or-create call against the real cloud collection; it was disclosed at the time.

### Lazy loading of heavy resources
- **What we did:** Models, clients and caches are created on first use, not at import: `SentenceTransformerEmbedder.model`, `rag.embeddings.get_embedder()`, `db.vectordb._get_client()`, the tiktoken encoding in `rag/context_builder.py` and the default semantic-chunker embedder. Module `__getattr__` keeps old names (`embedding_model`, `collection`, `tokenizer`) working.
- **Why (the problem it solves):** Importing a module should be cheap and side-effect free. Eager loading made every test and tool pay seconds for a model it did not use, made the import order matter, and put network access inside `import`.
- **Alternatives considered and why rejected:** Keep eager loading and mock it away in tests (hides the cost and the side effects); `functools.lru_cache` factories everywhere (fine, but the explicit `None`-until-used state is what the import tests assert on).
- **Trade-offs / what it costs:** The first call is slow and a failure (missing model, no credentials) surfaces at first use instead of at start-up. Lazy singletons are global state and need care with threads.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_import_guard.py::test_importing_everything_leaves_no_state` (no client, collection, embedder or tokenizer after importing everything) and `::test_embedder_construction_does_not_load_model`.
- **Likely interview questions and strong answers:**
  - *"Why load lazily?"* — "So import is free and predictable, tests do not pay for resources they do not use, and a missing dependency fails with a clear message where it is needed."
  - *"What is the downside?"* — "The first request is slow and errors move to runtime, so a production service should warm the resource explicitly at start-up."
- **Honest limitations:** The module-level singletons are not thread-safe on first creation; a service should initialise them before serving.

### A cheap token counter is not safe
- **What we did:** Stopped using a regex word counter as a size cap. Chunking now counts tokens with the embedder's own tokenizer (`count_tokens`, including [CLS]/[SEP]); the no-tokenizer fallback is a deliberately conservative WordPiece estimate (`estimate_token_count`) for tests only; ingestion re-checks every stored chunk with the real tokenizer.
- **Why (the problem it solves):** The model silently truncates input beyond 256 tokens, so anything past that is unsearchable, and nothing errors. A counter that looks right but undercounts hides that.
- **Alternatives considered and why rejected:** A fixed safety multiplier (it would cover most ordinary paragraphs but not chemical names or CJK text, which in an unsaved console probe ran several times above the regex count, so no fixed factor is safe); trust the character cap (2000 characters is not a token bound).
- **Trade-offs / what it costs:** Chunking needs the model's tokenizer loaded; the estimator makes test chunks smaller than necessary.
- **Evidence it works (test or measurement, with file path):** On the first 20 papers, chunks built with the plain regex counter reached 357 real tokens and 246 of 532 layout chunks, 213 of 620 semantic chunks and 22 of 748 recursive chunks were over 256; with the real tokenizer 0 of 600/677/764 were. Saved in `runs/measurements/chunk_coverage_20261121T090107Z/results.json` (key `token_counters_first_20`; fingerprint `8378f805…2842`; the estimator also gives 0 over 256, max 231). Tests: `test_real_tokenizer_token_cap`, `test_fallback_counter_is_safe_under_real_tokenizer`.
- **Likely interview questions and strong answers:**
  - *"Why not just count words?"* — "Because the model counts subword tokens, and the ratio varies with the text. On the corpus, chunks that passed a word-count cap reached 357 real tokens against a window of 256."
  - *"What is the source of truth?"* — "The tokenizer of the model that will embed the text, and a verification step that re-counts every stored chunk with it."
- **Honest limitations:** The estimator is a heuristic and undercounts accented/CJK stress text. The sample is 20 papers.

### Why recursive chunks reach 1,200+ characters when chunk_size is 1,000
- **What we did:** Traced it to the within-section merge: the splitter never exceeds `recursive_chunk_size` (1000), but a short tail chunk (under `min_chunk_chars`, 300) is merged into its predecessor inside the same section, which can add up to 299 characters. The effective cap is therefore `recursive_chunk_size + min_chunk_chars - 1` = 1,299 characters, far below the 2,000 hard cap and the 256-token cap. This is intended: it avoids stranding tiny tail chunks. A property test pins the bound (`test_recursive_effective_size_cap`).
- **Why (the problem it solves):** Without the merge, the end of every section becomes a fragment (a few words) that embeds poorly and dilutes retrieval.
- **Alternatives considered and why rejected:** Drop tails (loses content); keep tiny tails (noise); lower `chunk_size` so merged chunks stay near 1,000 (changes the strategy being compared).
- **Trade-offs / what it costs:** Chunk size is not uniform: 4.1% of chunks exceed 1,000 characters.
- **Evidence it works (test or measurement, with file path):** `runs/measurements/chunk_coverage_20261121T090107Z/results.json` (fingerprint `8378f805…2842`): the raw splitter's longest chunk is 1,000 in all 200 papers (7,347 raw chunks); after merging, 298 of 7,255 chunks (4.1%) exceed 1,000, the maximum is 1,290, and the median is 697. First 20 papers: maximum 1,200.
- **Likely interview questions and strong answers:**
  - *"Your chunk size is 1000 but you have 1200-character chunks. Why?"* — "A deliberate within-section tail merge; the bound is chunk size plus the minimum chunk size, and a property test enforces it."
- **Honest limitations:** The 1,299 figure is a configuration-dependent bound, not a constant; changing either setting changes it.

### Idempotent, incremental ingestion with verification
- **What we did:** `scripts/ingest.py` (logic in `rag/ingestion.py`) ingests the corpus for one strategy into the local store. A document is skipped when the store holds exactly its current `doc_version` (sha256 of the document text) and its chunk indices are complete (0..n-1). A changed or incomplete document has only its own chunks removed (`delete_by_doc`) and is re-chunked, re-embedded and upserted in batches of at most 300. A collection is never cleared. A signature of everything else that shapes the chunks (strategy, chunking config, embedder name and revision, token counter, and a hash of the chunker source files) is stored beside the collection; if it differs, ingestion refuses instead of silently keeping stale chunks. Batches are written last-first, so a crash leaves a detectable hole at the head, not an invisible truncated tail. After every run `verify_store` raises on any of: store count not equal to the sum of chunk counts; duplicate chunk ids; a corpus document with no chunk or a hole in its indices; a stored document not in the corpus; a seeded sample of 20 chunks whose text no longer matches its section text at `[char_start:char_end]`; any stored chunk over the real tokenizer's `max_seq_length`.
- **Why (the problem it solves):** v1 wiped the whole collection and re-ingested everything on every run, with random document ids, so nothing could be compared across runs and a failed run left an unknown state. Idempotence makes re-running safe; verification turns "it finished" into "the store matches the corpus".
- **Alternatives considered and why rejected:** Clear and rebuild (destructive, slow, loses the previous state); skip by document id only (misses edits); compare file mtimes (unreliable, and says nothing about content or config changes).
- **Trade-offs / what it costs:** Verification re-reads every stored chunk (about 20 s for 7,255 chunks). The skip check cannot detect a missing chunk at the very end of a document if the write order is ever changed; the reverse-order write is what covers that.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_ingestion.py` (14 tests: second run upserts nothing and skips all five documents; editing one document changes only its chunks; `delete_by_doc` leaves nothing retrievable; deleting a chunk by hand fails verification and the next run repairs only that document; a simulated crash mid-document is detected and repaired; tampered text fails the round trip; an orphan document fails verification but the manifest is still written; changed chunking config or embedder revision is refused). Real run, recursive strategy, 200 papers: first run ingested 200 documents and 7,255 chunks in 631.5 s with verification OK (`runs/ingest/recursive_20261121T083154586522Z/manifest.json`); the identical second command skipped 200, wrote 0 chunks, verified OK in 23.6 s (`runs/ingest/recursive_20261121T084245249585Z/manifest.json`). Code fingerprint in both: `70fa03b2…f531`.
- **Likely interview questions and strong answers:**
  - *"What happens when a document changes and you need to re-index?"* — "Its text hash changes, so only that document is deleted by id and re-ingested; everything else is skipped. If I change the chunking or the model instead, the stored signature no longer matches and ingestion refuses, so I build into a fresh collection rather than mixing old and new chunks."
  - *"What breaks at 100k documents?"* — "The per-document existence check is one store query per document, and verification reads every chunk; both need batching or a manifest table. Embedding time dominates (this run was 631 s for 200 papers on a CPU), so I would run it on a GPU or in parallel shards. The single local SQLite-backed Chroma and in-memory verification also need a server-mode store."
  - *"How do you know the store is correct, not just that the script finished?"* — "The run ends in a verification step that fails the process: counts, unique ids, coverage of every document, a seeded round trip against the source text, and a real-tokenizer check of every chunk."
- **Honest limitations:** Offset-confidence counts in the manifest cover only documents ingested in that run (the second run shows zeros). The round trip checks a sample of 20, not every chunk. The signature covers the chunker source files but not their dependencies (for example a langchain upgrade); `docs/env_baseline.txt` records those.

### One collection per chunking strategy
- **What we did:** `build_store(cfg, strategy)` opens a collection named `rag_<strategy>` (`rag_recursive`, `rag_layout`, `rag_semantic`) in the same local store. Only `rag_recursive` has been ingested.
- **Why (the problem it solves):** Chunking strategies produce different chunks of the same documents. Mixed in one collection they compete in the same nearest-neighbour search, and the evaluation can no longer say which strategy found a chunk. v1 mixed them and filtered on a metadata field.
- **Alternatives considered and why rejected:** One collection plus a `strategy` filter (every query pays the filter, a forgotten filter silently mixes strategies, and one strategy's re-ingest touches the others); a separate store directory per strategy (more paths to manage for no gain).
- **Trade-offs / what it costs:** Duplicated document text across collections, and a strategy comparison means building and ingesting each one.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_store.py::test_collection_is_per_strategy`. Collection created for the real run: `rag_recursive` with 7,255 chunks (`runs/ingest/recursive_20261121T083154586522Z/manifest.json`).
- **Likely interview questions and strong answers:**
  - *"Why not one collection with a metadata filter?"* — "An experiment should change one variable. Separate collections make the strategy a property of where you query, so you cannot accidentally mix them, and deleting or re-ingesting one cannot affect another."
- **Honest limitations:** Layout and semantic have not been ingested, so no strategy comparison exists yet.

### A persistent lexical index (SQLite FTS5) instead of in-memory BM25
- **What we did:** `rag/lexical.py` adds a `LexicalIndex` protocol and `SqliteFtsIndex`: an FTS5 table `chunks(chunk_id UNINDEXED, doc_id UNINDEXED, text)` with `tokenize='porter unicode61'`, ranked by FTS5's `bm25()` (negated so higher is better, ties broken by `chunk_id`). A small ordinary table `chunk_map` makes delete by chunk or document O(log N), because FTS5 `UNINDEXED` columns cannot be looked up by index. One file per strategy, `%LOCALAPPDATA%/advrag/lexical_<strategy>.sqlite3`, a sibling of the Chroma directory, OneDrive paths refused. User text is turned into OR-ed, double-quoted words, so quotes, hyphens, colons, parentheses, `*` and the words AND/OR/NOT/NEAR are plain terms: they can neither raise a syntax error nor act as operators. Ingestion writes both stores and verifies count and chunk-id parity; `scripts/build_lexical.py` backfilled the existing recursive store without re-embedding.
- **Why (the problem it solves):** The old BM25 was a module-level `BM25Okapi` built once at import from `collection.get(include=documents, metadatas)`. That meant: every process held the whole tokenised corpus in memory; each query scored every document in Python (O(N)); a single `get()` with no limit can be truncated by the service, which would silently shrink the index (I did not verify this service's limit); the index was stale until restart, so new documents were invisible to the lexical leg; and it ignored the metadata filter (see the next entry). Identity was `hash(document_text)`, which is randomised per process and collides for duplicate text.
- **Alternatives considered and why rejected:** Elasticsearch or OpenSearch (a service to run, secure and keep in sync, with no benefit at this scale); keeping `rank_bm25` and pickling it (still O(N) in Python, still whole-corpus in memory, still stale, no filter); Chroma's `where_document` substring match (not BM25 ranking).
- **Trade-offs / what it costs:** FTS5's tokenizer (Porter stemming, diacritic folding) and its BM25 variant differ from `rank_bm25` over `lower().split()`, so lexical results and any old number that depended on them are **not comparable**. That is an intended change, not a regression. A second store has to be kept in step with the vector store (hence the parity check and the crash-repair path). One SQLite connection is not thread-safe.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_lexical.py` (46 tests: 26 hazardous or empty queries never raise and never modify the table; `model NOT corpus` and `model AND zzzzqq` behave as plain words; `doc_id:` column syntax is not interpreted; the doc filter applies before the limit; porter and diacritics; persistence; OneDrive refusal) and `tests/unit/test_ingestion_lexical.py` (13 tests). Real backfill parity (store count equals lexical count and the chunk-id sets are identical, 0 missing and 0 extra): `runs/lexical/recursive_20261121T092841227285Z/parity.json`.
- **Likely interview questions and strong answers:**
  - *"What does BM25 index in production, and what happens at 10k / 100k / 1M chunks?"* — "It indexes the chunk text only, as an inverted index from stemmed terms to chunks; metadata such as doc_id is stored but not indexed and is applied as a filter. My measured size is 7,255 chunks, where nothing is stressed. What follows is reasoning, not measurement: at 10k it is trivial; at 100k a single SQLite file is still fine, but cost is driven by the posting lists of the query terms, so an OR query full of common words gets slower as the corpus grows, and there is one writer; at 1M the file is gigabytes, I would need stopword removal or a cap on query terms, checkpoint management, and probably a search server or sharding by document range."
  - *"Why not keep the in-memory BM25 you had?"* — "It was O(N) per query in Python, per-process memory, stale until restart, and it could not honour a filter."
  - *"Are your old BM25 results comparable?"* — "No, and I do not claim they are: different tokenizer and scoring variant."
- **Honest limitations:** No stopword removal and OR semantics: in the smoke run a long natural-language question gave a visibly noisier lexical leg than a keyword query (a qualitative impression, not a measurement). No query-term weighting or phrase boost. The recursive strategy is the only one built.

### Filter parity across retrieval legs
- **What we did:** `Retriever.retrieve(..., doc_ids=[...])` applies the same allow-list to both legs, before ranking and before the limit: Chroma `where={"doc_id": {"$in": [...]}}` for the vector leg, and `doc_id IN (...)` in the SQL `WHERE` of the FTS5 query for the lexical leg. An empty allow-list returns nothing and runs neither leg.
- **Why (the problem it solves):** In the old `retrieve_and_build_context`, `metadata_filter` was passed to the vector query only (`where=`); `_bm25_search` scored the whole in-memory corpus with no filter and its hits were fused with the filtered vector hits. So the lexical leg could return documents the caller had excluded. For paper-scoped evaluation (a Qasper question belongs to one paper) that leaks other papers into the candidates; for any multi-tenant use it is a tenant-isolation hole, because a filter the caller trusted was silently bypassed by half the retrieval.
- **Alternatives considered and why rejected:** Post-filter after retrieval (a filter applied after `LIMIT k` can return fewer than k, or nothing, even when matching chunks exist); filtering only inside fusion (the lexical candidates would already have been spent on excluded documents).
- **Trade-offs / what it costs:** The lexical filter is an `IN` list (capped at 30,000 ids) and only filters by `doc_id`; section or other metadata filters are not supported by the lexical leg yet.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_retriever.py::test_doc_filter_restricts_every_mode` (3 modes x 2 fusions x 3 allow-lists), `::test_filter_is_passed_to_both_legs`, `::test_filter_beats_relevance`, `::test_empty_allow_list_returns_nothing_and_calls_no_leg`, `::test_unknown_doc_filter_returns_nothing`, and `tests/unit/test_lexical.py::test_doc_filter_applies_before_the_limit`. Mutation check run during development: making the lexical leg ignore the filter fails 12 of these tests.
- **Likely interview questions and strong answers:**
  - *"What happens when metadata_filter is set?"* — "In the old code only the vector leg honoured it, so BM25 could return excluded documents. Now the allow-list is pushed into both retrieval queries before ranking, and a test asserts zero hits from other documents in every mode."
  - *"Is that enough for tenant isolation?"* — "Not by itself: it is correct at the retrieval layer, but the service layer must still derive the allow-list from the authenticated tenant, and that is not wired yet."
- **Honest limitations:** The API does not call the Retriever yet, so no deployed path is protected. Only `doc_id` filtering exists.

### Fusion bugs the tests now guard
- **What we did:** Moved fusion into the pure module `rag/fusion.py` (`weighted_rrf`, deterministic `fuse_rrf`, and a new `naive_interleave`) and made the Retriever truncate only after merging and only to a bound.
- **Why (the problem it solves):** (1) Truncating a concatenated list. In `scripts/run_evaluation.py` the "hybrid without RRF" branch builds `vec_rankings + bm25_rankings` and then keeps `ranked_ids[:candidate_k]`; the vector leg already returns `candidate_k` results, so no BM25 result can ever survive. By code reading, that ablation arm equals vector-only by construction, so **the earlier "hybrid versus vector" comparison is invalid evidence** (I have not re-run it; the code makes it impossible for the two to differ). (2) An unbounded fused list sent to the reranker. In `rag/retrieval.py` every fused item, up to the union of both legs, was put into `rerank_inputs` and scored by the cross-encoder, so reranker cost grew with the union instead of a chosen bound. The Retriever cuts the fused list to `rerank_k` (rerank on) or `top_k` (rerank off).
- **Alternatives considered and why rejected:** Keep `candidate_k` as the cap for everything (couples the retrieval width to the reranker budget); score-based merging (needs calibration between BM25 and cosine distance, see the RRF entry).
- **Trade-offs / what it costs:** With weights 1.0/0.7 RRF still lets the vector leg dominate the top ranks when the legs do not overlap: a lexical-only rank-0 hit scores 0.7/61 and falls behind roughly the first 26 vector ranks. A test pins that behaviour so changing the weights is a deliberate act. `naive_interleave` exists as a baseline that does guarantee lexical hits a place.

### Why RRF
- **What we did:** Hybrid retrieval fuses the two ranked lists with weighted Reciprocal Rank Fusion: score(id) = sum over legs of weight / (k + rank), with k = 60 and weights vector 1.0, lexical 0.7 (`config.yaml`).
- **Why (the problem it solves):** BM25 scores (unbounded, corpus-dependent) and cosine similarities (bounded, model-dependent) live on different scales, so adding or averaging them needs a calibration step. RRF uses only ranks, so it needs none, and it is robust to one leg returning a score distribution the other does not.
- **Alternatives considered and why rejected:** Weighted sum of min-max normalised scores (normalisation depends on the candidate set and is sensitive to outliers); a learned fusion or learning-to-rank model (needs labelled data I do not have yet); the round-robin `naive_interleave` (kept as a baseline, ignores how strong each hit is).
- **Trade-offs / what it costs:** RRF ignores score magnitude, so a very confident match and a barely relevant one at the same rank count the same. The weights 1.0/0.7 and k = 60 are **placeholders carried over from v1, not tuned**; they must be tuned on a dev split and then frozen before a held-out evaluation. With these weights the vector leg dominates unless the legs overlap (pinned by a test).
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_fusion.py::TestWeightedRRF::test_exact_scores` pins the formula; `tests/unit/test_retriever.py::test_chunk_found_by_both_legs_appears_once_with_both_ranks` checks the combined score against it. No retrieval-quality result exists for RRF versus alternatives.
- **Likely interview questions and strong answers:**
  - *"Why RRF, k=60 and weights 1.0/0.7?"* — "RRF because it needs no score calibration between BM25 and cosine. k=60 is the commonly used default from the original RRF paper; it damps the advantage of rank 1 over rank 2. The 1.0/0.7 weights are an untuned placeholder; the plan is to tune them (and k) on a development split, freeze them, and only then evaluate on held-out questions."
  - *"What is the weakness of RRF?"* — "It throws away magnitude, and with unequal weights the heavier leg dominates the top ranks when the legs do not overlap, which I pinned in a test."
- **Honest limitations:** No tuning has been done. The k = 60 default is quoted from memory of the original paper, not verified here.

### Span-based, length-neutral relevance
- **What we did:** `rag/eval_metrics.py` decides relevance from character spans. A retrieved chunk is relevant to a question when it has the same `doc_id` and section as a gold evidence span and the character overlap is at least `0.5 * min(len(span), len(chunk))`. Gold spans (`eval/gold_spans.py`) are the located evidence paragraphs, in the same section-relative coordinates as chunk offsets. Per question: HitRate@{1,5,10}, reciprocal rank, nDCG@10 (binary gain, ideal bounded by the number of relevant chunks that exist in the index), Doc-Hit@{1,5,10} and Evidence-Recall@{1,5,10} (fraction of the question's evidence paragraphs covered by some top-k chunk; an ambiguous paragraph counts once). The old rule (token-set F1 >= 0.25 against the evidence text, `eval/metrics.py`) is kept as separate `old_*` columns so the two can be compared.
- **Why (the problem it solves):** The old rule has two defects. F1 falls as the chunk grows, so a 2,000-character chunk that contains a 30-word evidence sentence scores as irrelevant, while a short chunk that merely shares vocabulary passes; that favours short, lexically similar chunks and so biases comparisons toward BM25 and small-chunk strategies. And it never checks which document the chunk came from, so in a corpus-wide search a lexically similar chunk of the WRONG paper counts as a hit.
- **Alternatives considered and why rejected:** Exact containment of the evidence in the chunk (a chunk that holds 90% of a paragraph would score zero, penalising chunk boundaries more than retrieval); overlap as a fraction of the span only (penalises short chunks inside long evidence); an LLM judge (cost, non-determinism, and generation is out of scope here).
- **Trade-offs / what it costs:** The unit of evidence is Qasper's annotated paragraph, so a chunk that covers half of a long paragraph counts even if the answer sentence is in the other half. The 0.5 fraction is a convention, not tuned. A chunk that could not be located at ingest (`char_start = -1`) can never be relevant.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_relevance.py` (17 tests): `test_long_chunk_containing_a_short_span_is_relevant_but_the_old_f1_metric_says_no` asserts both verdicts on the same 2,000-character chunk; a tiny overlap is not relevant; a different document or section is never relevant; the 0.5 boundary is exact in both directions (49 of 100 fails, 50 of 100 passes). The effect on real runs is visible in the saved dev runs (`runs/eval/20261121T103048Z_d7286f06_dev_corpus`): the `old_*` columns are far above the span-based columns in corpus mode. Those are DEV numbers, not claims, and I have not measured how much of the arm-to-arm differences the old rule distorted.
- **Likely interview questions and strong answers:**
  - *"How do you decide a chunk is relevant?"* — "By position, not by words: it must come from the annotated evidence paragraph, with at least half of the smaller of the two overlapping. That makes the rule neutral to chunk length, and it cannot be satisfied by a similar-sounding chunk from another paper."
  - *"Why keep the old metric?"* — "So the difference between the two rules can be shown, not asserted."
- **Honest limitations:** Whole-paragraph evidence is coarse. Five evidence paragraphs in the full usable set (two papers) occur more than once; every occurrence is accepted, and none of those questions is in the v2 set.

### Paired bootstrap with win/loss counts
- **What we did:** `eval/compare.py` compares two arms of one run on HitRate@5, MRR and nDCG@10. Per question it takes the difference (first arm minus second), reports the mean difference with a 95% percentile CI from 5,000 bootstrap resamples of the per-question differences (fixed seed), the number of questions where the first arm wins, loses and ties, a two-sided bootstrap p-value, and a Holm-adjusted significance flag computed across ALL comparisons made in the invocation, whose count is printed. A bare difference is never printed.
- **Why (the problem it solves):** The arms answer the same questions, so the per-question differences remove the question-to-question variation that dominates two separate means; a paired test is more powerful. A difference of two averages hides whether it is noise: the CI and the win/loss counts show it. Comparing many pairs and metrics makes some false positives certain, hence the multiple-comparison count and the Holm step-down (sort the p-values, compare the i-th smallest to alpha / (m - i), stop at the first failure).
- **Alternatives considered and why rejected:** Comparing two means (ignores pairing); a t-test on binary hit/miss differences (poor fit for 0/1 data and small n); a Bonferroni correction (valid but more conservative than Holm).
- **Trade-offs / what it costs:** The bootstrap treats questions as independent, but questions about the same paper are correlated, so these intervals are somewhat too narrow (a cluster bootstrap by paper would be more honest and is not implemented). The p-value has a resolution of about 1 in 5,000 and is an approximation.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_compare.py` (10 tests): on constructed data the CI contains the known difference; for identical arms the CI contains 0, wins = losses = 0 and the p-value is 1; results are deterministic for a fixed seed; the Holm flags match hand-computed cases; a report line always carries a CI and win/loss/tie counts and the comparison count. Dev example: the six requested pairs, 18 comparisons, are in the session log; no pair was flagged after Holm adjustment at this sample size (dev only, not a claim).
- **Likely interview questions and strong answers:**
  - *"Why paired?"* — "Same questions, same gold, so I compare per-question differences; that removes difficulty variation and is more sensitive than comparing two means."
  - *"You ran many comparisons. How do you control for it?"* — "I print how many were made and apply Holm across all of them, so a single lucky pair is not called significant."
- **Honest limitations:** Question-level resampling ignores same-paper correlation. With 174 dev answerable questions the intervals on hit rate are wide, so small differences cannot be detected.

### Latency methodology
- **What we did:** Latency is reported as `retrieval_latency_ms`: the time spent inside `Retriever.retrieve`, per stage (embed, vector, lexical, fuse, hydrate, rerank, total), measured by `perf_counter` inside the Retriever, with no sleeps in timed sections and metric computation outside them. Each arm first runs 5 warm-up requests (cache and lazy model load) whose results are discarded, the count is recorded, then every question is timed. The summary gives p50, p95 and max per stage, per arm. Hardware (platform, CPU, logical cores, RAM), Python and library versions are written into `config.json`. The label says "not end-to-end".
- **Why (the problem it solves):** The old summary (`scripts/run_evaluation.py`) pooled the latencies of every ablation configuration together before taking the percentile, so the headline "P50" described a mixture of arms, and it was an end-to-end time that included generation. The old "QPM" was `60 / mean total latency` of one configuration: a single-stream estimate dressed up as throughput, and a mean, which hides the tail.
- **Alternatives considered and why rejected:** Wall-clock around the whole script (includes loading and metric code); reporting a mean (hides tail latency); reporting QPM (it is not throughput without concurrency).
- **Trade-offs / what it costs:** The numbers describe retrieval on one machine with a warm process; they say nothing about cold start, concurrency or the LLM. Warm-up of 5 is a convention.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_retriever.py::test_every_stage_latency_is_measured` (a sleeping embedder, store and reranker prove each stage is really timed) and `tests/unit/test_eval_runner.py::test_run_writes_the_folder_with_all_files_and_checksums` (summary fields, warm-up count, label, hardware). Dev runs only; no latency number is published.
- **Likely interview questions and strong answers:**
  - *"What does your latency number mean?"* — "Retrieval only: time inside the retriever per query on a warm process on this machine, as p50, p95 and max, with the hardware recorded. It is not end-to-end and not throughput."
  - *"Why not report QPM?"* — "It was 60 divided by a mean latency, which assumes one request at a time and ignores the tail."
- **Honest limitations:** Single machine, single process, sequential requests, 4 logical cores. Corpus and paper modes differ in work done, so their latencies are not comparable.

### Why unanswerable questions are excluded from retrieval metrics
- **What we did:** Unanswerable questions (48 usable; 19 dev, 29 test) stay in the golden set and the split but are not scored by `run_retrieval_eval.py`; `config.json` records how many were not scored.
- **Why (the problem it solves):** Retrieval metrics ask "did the system surface the evidence?". An unanswerable question has no evidence, so every metric is undefined or trivially zero, and averaging those zeros in would lower every arm by the same arbitrary amount and make runs with different proportions of unanswerable questions incomparable. The correct behaviour on such a question is to refuse, which is a generation question (does the answer say it cannot find the information?).
- **Alternatives considered and why rejected:** Score them as zero (arbitrary deflation); define a "correct retrieval" for them (for example top score below a threshold: that is a calibration question that belongs with abstention).
- **Trade-offs / what it costs:** Retrieval evaluation says nothing about abstention; that waits for the generation evaluation.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_eval_runner.py::test_run_writes_the_folder_with_all_files_and_checksums` (unanswerable questions never appear in `per_question.jsonl`; the count is in `config.json`).
- **Likely interview questions and strong answers:**

- **Honest limitations:** A retriever that returns confident-looking junk for an unanswerable question is not penalised anywhere yet.

### Retrieval is not bit-reproducible across processes (HNSW)
- **What we did:** Ran the same dev evaluation twice per mode in fresh processes and checked the per-question rows with `eval/determinism.py`, which separates "metrics" from "retrieved lists" from timing.
- **Why (the problem it solves):** I had expected retrieval to be deterministic. In paper mode (a filtered search) the two runs were identical in all 1,044 rows apart from timing. In corpus mode all per-question metrics were identical in all 1,044 rows, but the retrieved lists differed in 3 rows (arms D, E, F), at ranks 8 to 10 or in the vector rank of a lexical hit. Reproduced outside the harness: the same query on the same index, in 6 fresh processes, returned two different orderings (a chunk at rank 8 appears or not). Within one process repeats were identical. Chroma's HNSW search is approximate and not bit-reproducible across processes, even with `ef_search` = 100.
- **Alternatives considered and why rejected:** Exact brute-force search over stored vectors for evaluation (deterministic, but it would evaluate something other than the production vector leg); ignoring it (it would let a future run "differ" without anyone knowing why).
- **Trade-offs / what it costs:** Results can differ by deep-rank noise between runs; a change that happens to flip a relevant chunk in or out of the top k would change that question's metrics. The comparison tooling reports metric equality and list equality separately so this is visible.
- **Evidence it works (test or measurement, with file path):** `runs/eval/20261121T103048Z_d7286f06_dev_corpus` versus `runs/eval/20261121T103209Z_d7286f06_dev_corpus` (3 of 1,044 rows differ in `retrieved`, 0 in metrics) and `..._dev_paper` pair (0 differences); `tests/unit/test_eval_runner.py::test_a_changed_retrieved_list_with_equal_metrics_is_reported_separately`.
- **Likely interview questions and strong answers:**
  - *"Is your evaluation deterministic?"* — "The metrics were identical across two runs, but not strictly the retrieved lists: the approximate vector index can swap deep-ranked results between processes. I measured it, report it, and my tooling separates the two."
- **Honest limitations:** Two runs per mode is a small sample of how often this happens; I have not measured the ANN recall against exact search.

### Offsets are computed, never searched for
- **What we did:** Replaced the `str.find` locate loop in `recursive_chunk` with an offset-native splitter, `rag/splitting.py::recursive_split_spans`. It performs the same recursive separator split as LangChain's `RecursiveCharacterTextSplitter`, but carries absolute `(start, end)` positions through every split and merge, so a chunk's `char_start`/`char_end` are computed, never looked up. `rag/tokens.py::split_to_fit_spans` does the same for token-limit re-splits, and `semantic_chunk` computes paragraph spans natively (`_paragraph_spans`) and maps re-split pieces back with `bisect`. Chunkers now emit `section_char_start`/`section_char_end`; `rag/chunk_adapter.py` verifies them (exact or whitespace-normalised) and only searches as a fallback when a chunker reports no offsets (counted as `offsets_located_by_search_ingested_docs_only` in the ingest manifest; 0 in all four new runs). A static test (`tests/unit/test_splitting.py::test_chunking_modules_never_search_for_a_position`, over the chunker, tokens and splitting modules) fails if any of them ever calls `find/rfind/index/rindex` again. Behaviour change: none on real data (see evidence); semantics of `chunk_size`, `overlap`, `min_chunk_chars` and the within-section merge are unchanged.
- **Why (the problem it solves):** The old loop searched for each chunk's text starting from "previous end minus overlap". In text with a period (a repeated sentence, boilerplate, a table-like passage) the search can match one period too early. The chunk text is right but its offset is wrong, and a merged tail is sliced from the wrong place, so the last paragraph can silently vanish. Offsets are what make citations point at the right characters and what the span-based relevance labels (`rag/eval_metrics.py::is_relevant`) and paragraph Evidence-F1 are computed from: a drifted offset means a wrong relevance label, silently. It was found by a property test (coverage: every non-whitespace source character lies in some chunk) on a generated periodic input.
- **Alternatives considered and why rejected:** Keep `find` but search from a better start (still a search; it can always match a repeat); mark the property test expected-to-fail (it hides the bug and any different recursive coverage failure; you rejected it); fix only the adapter (the chunker would still slice the wrong text, the adapter would just agree with the wrong offset). Fixed before the test-split freeze even though the audit of the 200 real papers had found 0 affected chunks (`runs/measurements/store_audit_20261121T105815Z/results.json`): the correctness of citations and labels should not depend on the corpus happening to be non-periodic, and re-ingesting is cheap now and expensive after a freeze.
- **Trade-offs / what it costs:** A new 100-line module to maintain; the old LangChain splitter is kept only as a test oracle. Changing chunker source changes the ingest signature, so everything was re-ingested into a new store (`%LOCALAPPDATA%\advrag\chroma_v2`; the old stores are kept). While doing this I found a real gap: `rag/splitting.py` was not part of the signature hash, so editing it would not have invalidated stores; it is now included, and `tests/unit/test_ingestion.py` checks the signature covers every `rag.*` module the chunkers import (excluding `rag.embedders`).
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_splitting.py` (12 tests): the new splitter equals frozen copies of the LangChain-based reference on all 2,958 real sections and on Hypothesis-generated text; `tests/unit/test_chunker_properties.py::test_regression_recursive_chunker_covers_periodic_text` (the old strict xfail now passes as a normal test) and `test_offsets_are_computed_and_slice_back_to_the_chunk_text`. Re-ingest: `scripts/compare_stores.py` on old versus new stores found 0 changed chunk ids and 0 differing text, section, `char_start` or `char_end` fields for 7,255 recursive and 6,442 semantic chunks (`runs/measurements/store_compare_20261121T121030Z/results.json`, `..._121038Z/results.json`); `scripts/audit_store_text.py` on the new stores: 0 chunks differing from the source slice, 0 uncovered characters (`runs/measurements/store_audit_20261121T121006Z`, `..._121020Z`); ingest manifests in `runs/ingest/` show all offsets `exact`.
- **Likely interview questions and strong answers:**
  - *"Why did you rewrite a working chunker?"* — "A property test I wrote found that on periodic text the offset search can land a period early and silently drop content. Real papers were unaffected, and I measured that. But offsets drive citations and my relevance labels, so I made them computed by construction and added a test that forbids searching, then proved the new splitter equals the old one on all real sections."
  - *"How do you know the re-ingest didn't change anything?"* — "I diffed the two stores chunk by chunk: same ids, same text, same offsets."
- **Honest limitations:** Equality with the old splitter is proven on 2,958 real sections and generated text, not on all possible inputs. The adapter still has a search fallback for chunkers that report no offsets; it is counted and was never used in the final ingests.

### Deterministic property tests
- **What we did:** Registered two Hypothesis profiles in `tests/conftest.py`: `ci` (default; `derandomize=True`, no example database; used by normal and `--fast` runs) and `explore` (random seeds, `print_blob`), selected with `ADVRAG_HYPOTHESIS_PROFILE`. The minimal failing input is pinned as a permanent `@example` on the coverage test, and the old strict-xfail known-bug test became an ordinary regression test. `FAST_EXAMPLES` = 8, `FULL_EXAMPLES` = 200. `tests/unit/test_hypothesis_profiles.py` checks the profiles.
- **Why (the problem it solves):** The coverage test passed when run alone and failed in the full suite. Hypothesis' `HypothesisProvider` collects literal constants from the project modules found in `sys.modules`, so the examples it generates depend on which test modules have been imported. A test whose verdict depends on which other tests are collected is a reproducibility bug: it makes "it's green on my machine" meaningless and lets a real bug hide.
- **Alternatives considered and why rejected:** An xfail marker (hides the bug); lowering the example count (hides it more often); trying to switch the constants provider off (there is no supported opt-out in the installed version); fixed `seed` only (still module-set dependent, so not enough on its own).
- **Trade-offs / what it costs:** `derandomize` makes the CI run deterministic only for a fixed set of collected modules, and it explores fewer inputs per run than random seeding would across many runs. Every bug found by exploring must be pinned with `@example`, or CI will not keep finding it. Exploration is therefore a deliberate, separate command.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_hypothesis_profiles.py`; `tests/unit/test_chunker_properties.py` (`@example` on the coverage test); the old xfail XPASSing against the fixed chunker confirmed the fix. Commands are in `CLAUDE.md` rule 8.
- **Likely interview questions and strong answers:**
  - *"How do you make property-based tests reproducible?"* — "Derandomized CI profile, every discovered failure pinned as an `@example`, and a separate explore profile with random seeds for finding new ones. I learned the hard way that Hypothesis can depend on which modules are imported, so I treat a test whose outcome changes with collection as a bug."
- **Honest limitations:** The root-cause explanation (module-constants seeding) is supported by bisecting which module import flipped the outcome and by reading the library, not by a patched-library proof. The CI profile covers fewer inputs than explore.

### Clustered bootstrap
- **What we did:** `eval/compare.py` now reports a paper-clustered paired bootstrap as the PRIMARY interval and p-value: it resamples papers with replacement, keeps all of a paper's questions together, and computes the question-weighted mean difference per resample (5,000 resamples, fixed seed). The per-question bootstrap remains as a secondary column; Holm correction runs on the clustered p-values across all comparisons in an invocation. Output always shows `n_q`, `n_pap`, both CIs and wins/losses/ties.
- **Why (the problem it solves):** Up to 3 questions come from the same paper, and they share a topic, vocabulary and often evidence region, so they are correlated. Resampling questions treats them as independent and understates the uncertainty (intervals too narrow, too many false "significant" results). The unit of independence is the paper.
- **Alternatives considered and why rejected:** Per-question bootstrap alone (understates uncertainty); a paired t-test/Wilcoxon on questions (same independence problem, and metrics like hit rate are not normal); mixed-effects models (heavier, and less transparent for an interview setting).
- **Trade-offs / what it costs:** Wider intervals and less power; with 71 dev papers the clustered CI is only modestly wider than the per-question one, but it is the honest one. Bootstrap p-values have resolution about 1/5,001.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_compare.py` (17 tests), including `test_clustered_ci_is_wider_when_all_questions_of_a_paper_are_identical_copies`; identical arms give a CI containing 0 with wins = losses = 0.
- **Likely interview questions and strong answers:**
  - *"Why resample papers, not questions?"* — "Questions about the same paper aren't independent. If I resample questions I pretend I have more independent evidence than I do. I resample the cluster, keep its questions together, and I show the per-question interval next to it so you can see how much narrower it would have been."
- **Honest limitations:** With few papers per split the bootstrap itself is noisy; Holm assumes the comparisons I list are the whole family, and ad-hoc extra comparisons outside one invocation are not corrected.

### Qasper's canonical setting and metrics
- **What we did:** Made PAPER mode (`doc_ids=[gold paper]`) the primary setting of the evaluation (`--mode` defaults to `paper`; `setting` and `primary_setting` are written into `config.json` and `summary.json`; `compare.py` prints a `SETTING:` line) and labelled corpus-wide mode "EXTENSION: corpus-wide". Added paragraph-level Evidence-F1 (`rag/eval_metrics.py::evidence_f1`, `evidence_f1_at_k`): map each retrieved chunk to the source paragraphs its offsets overlap, take the F1 of that paragraph set against each annotator's evidence paragraph set, and take the max over annotators. `golden_set_v2.json` now stores every annotator's reference (`answer`, `type` = extractive / abstractive / yes_no / unanswerable, `evidence`) without changing which questions are selected or the split.
- **Why (the problem it solves):** In Qasper, annotators wrote questions after reading only the title and abstract of ONE paper, and the official task is single-document: given the paper, answer the question and identify the evidence paragraphs. The official metrics are Answer-F1 and Evidence-F1, each taking the maximum over the multiple annotators' references, because several different answers or evidence sets can be valid. Reporting only a corpus-wide number evaluates a task the dataset was not designed for. Corpus mode is kept because the production system is corpus-wide, but it is secondary.
- **Alternatives considered and why rejected:** Corpus mode only (it is the production setting but not the dataset's task, and its null result is hard to interpret); first annotator only (arbitrary and lower-agreement); a chunk-level F1 (chunk boundaries differ per strategy, so strategies would not be comparable; paragraphs are strategy-neutral).
- **Trade-offs / what it costs:** Evidence-F1 is precision-sensitive, so it falls as k grows (it measures "how clean is the retrieved set", unlike HitRate, which only rises); paragraph identity is the paragraph text (as in the official code), so duplicate paragraphs collapse; 35 of 822 annotator answers have only table/figure evidence, which is not retrievable and is skipped in the max (a question with no usable annotator is `None`, not 0). Answer-F1 needs generation and is deliberately not measured here.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_evidence_f1.py` (17 hand-built cases), `tests/unit/test_eval_runner.py::test_evidence_f1_is_computed_from_the_annotator_references_and_the_corpus`, `::test_paper_mode_is_the_primary_setting_and_corpus_mode_an_extension`, `::test_the_default_mode_is_paper`, `::test_compare_prints_the_setting_label_of_the_run`. Annotator answers by type in the golden set: 529 extractive, 204 abstractive, 89 yes/no, 72 unanswerable (`eval/datasets/qasper_dev/golden_set_v2.json`).
- **Likely interview questions and strong answers:**
  - *"What does Qasper measure and how did you follow it?"* — "Single-document QA over NLP papers. Questions are written from the title and abstract, so the canonical task gives the model the paper. Official metrics are Answer-F1 and Evidence-F1 with a max over annotator references. I made paper mode the primary retrieval setting, implemented Evidence-F1 the same way, and kept corpus-wide retrieval as a labelled extension because that is how the product is used."
- **Honest limitations:** My Evidence-F1 is computed on retrieved paragraphs, not on a model's selected evidence, so it is not the official leaderboard number; Answer-F1 is not implemented in this step.

### Pre-registration and the decision rule
- **What we did:** Before running any new configuration of Stage 2a, wrote `eval/PREREGISTRATION.md` and recorded its sha256 (`eval/PREREGISTRATION.sha256`; every new run's `config.json` carries `preregistration.sha256_original_text`, and the runner refuses to run if the original text no longer matches). It fixes: the primary setting (paper mode) and metric (nDCG@10) and the four secondary metrics; the complete list of dev configurations (15 paper-mode arms: the six old ones, two reranker arms, a 2 x 3 RRF grid, a stopword-filtered lexical arm and its hybrid, plus a title-qualified corpus run and a depth-20 diagnostic run); the number of comparisons (109 in five Holm families); a parsimony decision rule (the simplest arm whose paper-clustered CI versus the best arm includes 0, with an explicit complexity score per arm); and the exact test-split comparisons (A vs frozen, D vs frozen, F vs frozen, frozen vs frozen+reranker). Later changes are only allowed as a dated `## Deviations` section; six were recorded (none changes an arm, metric or rule). `scripts/decision_rule.py` applies the rule mechanically and `tests/unit/test_stage2a_analysis.py::test_complexity_matches_the_table_in_the_preregistration` checks that the code's complexity score equals the table in the document.
- **Why (the problem it solves):** Trying many configurations on dev and reporting the best one inflates the result (the maximum of 15 noisy estimates is biased upward: the winner's curse), and each extra look is another chance to pick noise. Writing the grid, the metric and the selection rule down first turns "which one looks best" into a procedure that cannot be adjusted after seeing the numbers. The parsimony rule adds a second guard: when differences are within noise, prefer the cheaper, simpler system, which also generalises and costs less to run.
- **Alternatives considered and why rejected:** Pick the best dev arm (selection bias); a held-out test comparison of all 15 arms (burns the test set and needs a 15-way correction); Bonferroni (more conservative than Holm for no gain); a rule using Holm-adjusted intervals only (the owner specified the unadjusted clustered CI; the Holm outcome is reported as a sensitivity check).
- **Trade-offs / what it costs:** Rigidity: a good idea that occurs after seeing results (e.g. a different reranker) is out of scope for this stage and must be a new, separately pre-registered step. The unadjusted CIs in the rule are narrower than Holm-adjusted ones, so the rule can lean towards the more complex arm.
- **Evidence it works (test or measurement, with file path):** `eval/PREREGISTRATION.md` (+ `.sha256`); the five run folders' `config.json`; `tests/unit/test_eval_runner.py::test_the_preregistration_hash_is_recorded_and_tampering_is_refused`; `runs/measurements/20261121T132151Z_decision_rule/results.json`. DEV-ONLY outcome of the rule on run `runs/eval/20261121T125301Z_0d717273_dev_paper`: BEST by mean nDCG@10 = H (D + rerank on the semantic store, complexity 6), 9 of the other 14 arms were statistically indistinguishable from it on the unadjusted clustered CI, and the least complex of those is D (complexity 3); the Holm sensitivity version gives A (vector only). Both are stated, nothing is frozen. The RRF grid showed no setting different from the current default (all clustered CIs include 0; `runs/analysis/20261121T_stage2a_compare/P1_paper_primary_nDCG10.txt`).
- **Likely interview questions and strong answers:**
  - *"How do you avoid overfitting to your eval set?"* — "I split by paper, pre-registered the grid, the metric and a parsimony rule with a hash before running, and I fixed the exact test comparisons. The test set is touched once, and a ledger proves it."
  - *"Why prefer a simpler system if a complex one scores higher?"* — "Because the difference was within noise, and the simple one is cheaper, easier to maintain and less likely to be the product of selection."
- **Honest limitations:** The complexity score is my own convention (a reranker costs two points); the rule's outcome depends on it. Dev only (71 papers). A snag worth admitting: the first version of the hash check mishandled the file's CRLF line endings after I appended the deviations section; I fixed the tool (not the text), re-verified that the original text still hashes to the recorded value, and wrote it down as deviation 6.

### Fusion improves ranking, not coverage
> **DEV ONLY** until the test run. Not a claim; no number here may go to README or the claims log.
- **What we did:** Compared vector-only (A), RRF hybrid (D), and the other arms in paper mode on the dev split, and looked at which metrics move. ### Local cross-encoder reranker: result and latency cost
> **DEV ONLY.**
- **What we did:** Added `rag/rerankers.py::CrossEncoderReranker` (the injected callable the Retriever already accepts): `cross-encoder/ms-marco-MiniLM-L-6-v2` at pinned revision `233902d25c440f23af6f7d6e94d2946bac0bee0a` (recorded in `config.yaml`), downloaded once, then loaded lazily from the local cache only. Arms G = D + rerank and H = F + rerank: rerank the first `rerank_k=20` fused candidates, keep the top 10. Reranker latency is its own stage (`rerank`).
- **Why (the problem it solves):** A cross-encoder reads query and chunk together and is usually a better judge than the embedding model; the question is whether the gain is worth the latency on CPU.

- **Trade-offs / what it costs:** About 1.4 s extra per query on CPU, a model to ship and version, and an extra failure mode. `reranker_enabled` stays false in `config.yaml`.
- **Evidence it works (test or measurement, with file path):** `runs/eval/20261121T125301Z_0d717273_dev_paper/summary.json` and `..._130339Z_...` (latency per stage, warm-up discarded, n = 174 per arm); `tests/unit/test_rerankers.py` (lazy, local-only, missing cache raises instead of downloading, real model scores a relevant passage higher); `tests/unit/test_eval_runner.py::test_end_to_end_all_fifteen_arms_with_a_fake_reranker_and_the_titled_mode`.

### Streaming with inline citations and a typed result
- **What we did:** The model streams plain text with inline `[S1]` markers; `rag_core/service.py::RagService.answer_stream` yields `sources` (the passages sent, labelled S1..Sn, before any token), `token`, `error` and exactly one final `done` carrying an `AnswerResult` (pydantic: answer, short_answer, citations, invalid_citations, abstained, used_sources, retrieved_sources, provider, model, finish_reason, usage, latency_ms {retrieve, first_token, total}, degraded, partial, cached, errors, attempts). `rag_core/citations.py` validates each marker against the labels that were actually sent: valid ones go to `citations`, unknown ones (`[S9]` with five sources) to `invalid_citations`; markers inside fenced or inline code are ignored; `[S1][S2]` and `[S1, S2]` are two citations. The sentinel `INSUFFICIENT_CONTEXT` sets `abstained=True`, is held back while it is still being spelled out and is never streamed (the UI shows its own message). `answer_short` uses a short-answer prompt and returns a non-streaming result for evaluation.
- **Why (the problem it solves):** The UI needs tokens as they arrive (a first token quickly matters more than the whole answer) and the evaluation needs structure. Streaming JSON cannot be parsed until it is complete and a truncated or malformed document loses everything; plain text with inline markers degrades gracefully (a cut-off answer is still readable) and the structure is derived afterwards by code, which can be tested. `used_sources` holds exactly the chunks sent to the model (id, label, text, as truncated if truncated), so context recall and any later RAGAS-style evaluation describe what the model really saw, not what retrieval returned.
- **Alternatives considered and why rejected:** Streaming JSON or a structured-output schema (cannot stream a validated object; one syntax slip loses the answer); a final "citations" call (a second model call to say what the first one meant); parsing citations by string similarity between answer and sources (heuristic and slow).
- **Trade-offs / what it costs:** The model must follow the marker convention; a model that ignores it yields an answer with no citations, which the service reports (and does not cache) rather than repairing. The abstention hold-back delays the first visible token by the length of the first few characters.
- **What the validator cannot prove:** A valid marker means "the model pointed at a source that exists in this prompt". It does NOT mean the source supports the claim, that the claim is complete, or that nothing was invented around the marker. Whether the answer is faithful to the sources is a separate question that needs a faithfulness evaluation (claim-by-claim entailment against `used_sources`), which has not been built or run yet.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_citations.py` (malformed markers, `[S1][S2]`, `[S9]` with five sources, code spans, abstention), `tests/unit/test_rag_core_service.py::test_used_sources_are_exactly_the_chunks_sent_to_the_llm` and `::test_event_order_sources_then_tokens_then_done_with_a_typed_result`, `tests/unit/test_rag_core_integration.py` (real Retriever, tmp stores). I also injected six deliberate bugs (escaping removed, sentinel hold-back removed, oversize first chunk dropped, cache of degraded results, retry after a mid-stream failure, cache key blind to the prompt version) and checked that the intended tests fail for each, then reverted them.
- **Likely interview questions and strong answers:**
  - *"How do you know the citations are right?"* — "I know they are well-formed and point at passages that were actually in the prompt. I do not know that the cited passage supports the claim; that needs a faithfulness evaluation, which is the next step and which I have not run."
  - *"Why not structured output?"* — "Because I want tokens on screen early, and a streamed JSON document is unusable until it closes. Inline markers plus a parser I can unit test gave me streaming and structure."
- **Honest limitations:** No live provider was exercised (no keys were available; the smoke script is written and skipped); prompt wording is untested against a real model; citation behaviour of the real models (do they cite in this format?) is unknown until the smoke run.

### Failover only before the first token
- **What we did:** `rag_core/gateway.py::LLMGateway` tries providers in order (Groq, then Gemini). A call that fails before it yielded any text is retried on the same provider when the error is retryable (429, 5xx, timeout, connection) with exponential backoff and jitter, at most three attempts, honouring a server `Retry-After` up to a cap; 4xx errors (auth, not found, bad request) are not retried, but the next provider is tried. Once a provider has yielded a token and then fails, the gateway raises a typed `MidStreamError` carrying the partial text and the attempt records: no retry, no second provider. The service turns it into an `error` event (`mid_stream`, not recoverable) and a `done` with `partial=True`, the text received and `finish_reason="error"`.
- **Why (the problem it solves):** Switching providers mid-answer would splice text written by two different models into one sentence: the user would read an answer nobody wrote, citations could point at sources the second model never saw it reasoning about, and a cache could store the hybrid. Before the first token nothing has been shown, so retrying or switching is invisible and safe. The typed error gives the UI the three things it needs: what was received (show it, marked as incomplete), that it is not recoverable by the system (offer "retry"), and which provider failed.
- **Alternatives considered and why rejected:** Resume the answer on the second provider with the partial text as a prefix (the second model would continue in its own voice and could contradict the first part; also doubles the prompt cost); buffer the whole answer before showing anything (removes the streaming benefit and just moves the problem to the timeout); retry the same provider mid-stream (re-generates different text after the user has already read part of it).
- **Trade-offs / what it costs:** A failure at token 200 of 300 gives the user an incomplete answer and a retry button instead of a transparent recovery. A circuit breaker per provider (opens after three consecutive failed calls, half-open after a cooldown with exactly one trial call) avoids paying a timeout on every request while a provider is down; a 400-class error (about one request) is deliberately not counted against the provider so a user cannot open a breaker with a malformed prompt.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_gateway.py::test_MIDSTREAM_failure_raises_a_typed_error_and_does_not_retry_or_fail_over`, `::test_failover_before_the_first_token_primary_fails_immediately_secondary_answers`, `::test_the_breaker_opens_after_n_consecutive_failed_calls_and_stops_calling_the_provider`, `::test_half_open_after_the_cooldown_one_trial_call_then_closed_on_success`, `::test_a_failed_half_open_trial_re_opens_the_breaker_for_a_full_cooldown`, `::test_429_is_retried_with_exponential_backoff_then_succeeds`, `::test_4xx_errors_are_not_retried_on_the_same_provider`; `tests/unit/test_rag_core_service.py::test_MIDSTREAM_failure_yields_an_error_event_a_partial_result_no_failover_and_no_caching` and `::test_failover_before_the_first_token_answers_from_the_second_provider_and_is_not_cached`. The two SDK wrappers are tested with fake clients and the REAL `openai` and `google-genai` exception classes (status-to-kind mapping, key scrubbing). A bug carried over from v1: passing `config={"timeout": 30}` to `google-genai` is rejected by pydantic on every call; the timeout belongs in `HttpOptions` (milliseconds), per request, with the SDK's own retries switched off so the gateway owns the policy (`test_the_old_gemini_bug_...`, `test_gemini_timeout_goes_into_http_options_in_milliseconds_...`).
- **Likely interview questions and strong answers:**
  - *"What happens when the LLM provider goes down mid-stream?"* — "The user keeps what was already shown, marked incomplete, with a retry; I do not stitch another model's text onto it. Before the first token I fail over silently."
  - *"Why a circuit breaker?"* — "Without one, every request pays the full timeout while a provider is down. The breaker fails fast and probes with a single trial call after a cooldown."
- **Honest limitations:** The per-call timeout is enforced by the SDK's HTTP timeouts (connect and between chunks), not by a hard wall-clock cut of a slow-but-alive stream; the gateway's total deadline only stops NEW attempts. Whether the real providers raise the exception types my wrappers map was verified against the SDK classes, not against live errors.

### Never cache errors; cache keys carry versions
- **What we did:** `rag_core/cache.py`: a `CacheBackend` protocol and an in-memory, size-bounded LRU with a per-entry TTL (thread-safe, values copied in and out). The key is a sha256 over the normalised question (NFKC, lower case, collapsed whitespace), the document filter (order-insensitive), a hash of the retrieval and context settings (mode, fusion, candidate_k, rerank, rrf_k, weights, top_k, context budget), the index version (chunk count and the ingest-manifest hash, or the ingest signature when no manifest file is given), the embedder revision, `PROMPT_VERSION`, the generator model id, top_k and the answer mode. Only a successful, complete, validated answer is stored: no errors, no degraded notice, no partial stream, no abstention, no invalid citation, no long answer without a citation, no `finish_reason` other than "stop", and nothing produced by a fallback model (the entry is keyed on the primary model's id).
- **Why (the problem it solves):** The v1 cache keyed on the lower-cased query alone. A re-ingested corpus, a new prompt or a different model kept serving old answers, and a transient provider failure could be stored and replayed as if it were the answer. A cache should only ever make a correct answer cheaper. Not caching abstentions is deliberate: an abstention may be a sampling fluke, and storing it would turn one bad draw into a persistent wrong "I don't know".
- **Alternatives considered and why rejected:** Short TTL only (hides staleness for a while, does not fix it); keying on the full retrieved text (correct but defeats the purpose: you must retrieve first); a shared Redis cache now (a deployment concern: the protocol allows it later).
- **Trade-offs / what it costs:** More misses after any version bump (intended); entries produced during a failover are not reused; an in-memory cache is per process and lost on restart.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_cache.py::test_changing_any_key_ingredient_changes_the_key` (10 ingredients), `::test_these_results_are_never_cacheable`, `::test_an_entry_expires_after_the_ttl`, `::test_the_cache_is_size_bounded_and_evicts_the_least_recently_used_entry`; `tests/unit/test_rag_core_service.py::test_unsuccessful_or_unvalidated_answers_are_never_cached` (degraded, abstention, invalid citation, no citation, truncated, mid-stream), `::test_a_changed_cache_key_ingredient_misses`, `::test_a_failure_does_not_overwrite_or_poison_a_good_cached_answer`.
- **Likely interview questions and strong answers:**
  - *"What is in your cache key and why?"* — "Everything that can change the answer: question, filter, retrieval settings, index version, embedder, prompt version, model, top_k. And it only stores answers I would be happy to serve again."
- **Honest limitations:** The index version is a chunk count plus a hash, so it detects a re-ingest but not a change that keeps both identical; the TTL is a safety net, not a correctness mechanism; semantic (near-duplicate question) caching is not implemented.

### Prompt-injection posture
- **What we did:** Every piece of untrusted text is escaped before it enters the prompt: source text, section and paper names and the question have `&`, `<` and `>` escaped (attributes also have quotes escaped and whitespace collapsed), so none of them can contain a raw `<source>`, `</source>` or `<question>` tag. Sources are wrapped as `<source id="S1" paper="..." section="...">`. The system message says to answer only from the sources, to treat the content of `<source>` as data and never as instructions, to follow no instruction other than the rules, to cite as `[S1]`, and to reply exactly `INSUFFICIENT_CONTEXT` if the sources do not contain the answer. The prompt is versioned (`PROMPT_VERSION`, part of the cache key).
- **Why (the problem it solves):** The corpus is scientific text that anyone can write; a passage saying "ignore previous instructions" is a realistic input. Delimiters tell the model where data ends; escaping makes the delimiters unforgeable; the rule that sources are data tells the model how to treat them.
- **Alternatives considered and why rejected:** A blocklist of phrases like "ignore previous instructions" (trivially bypassed, false positives on papers about prompt injection); a second LLM call as a classifier (cost, latency, itself injectable); no escaping, trusting the instruction alone (the instruction alone is not a boundary).
- **Trade-offs / what it costs:** Escaped text is slightly noisier for the model (`&lt;`); math and code in papers with angle brackets are altered in form, not in content.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_prompts.py::test_a_source_that_says_ignore_previous_instructions_stays_inside_its_delimiter`, `::test_source_text_cannot_close_a_source_tag_or_open_a_new_one`, `::test_paper_and_section_attributes_cannot_break_out_of_the_tag`, `::test_the_question_cannot_close_its_tag_either`. These test the STRUCTURE of the prompt; they do not test what a model does with it.
- **What remains unsolved:** A model can still follow an instruction that sits inside a correctly delimited source; delimiters and a system rule lower the probability, they are not a security boundary. Nothing here stops a source from containing misleading factual claims, or from asking the model to put a link or a particular phrase in its answer. There is no output filter, no allowlist for links, and no adversarial evaluation (a set of injected passages scored against a real model) yet. The model has no tools or actions, so the blast radius is limited to the text of the answer; that is a property of this design, not of the prompt.
- **Likely interview questions and strong answers:**
  - *"How do you defend against prompt injection?"* — "In layers that reduce the risk: escape untrusted text so it cannot forge a delimiter, delimit it, tell the model it is data, and give the model no tools. I do not claim it is solved: I have not run an adversarial evaluation against a real model."
- **Honest limitations:** See "What remains unsolved". The strongest claim I can make is about the prompt's structure.

### Degraded mode instead of a crash
- **What we did:** If every provider fails or its breaker is open before any text, `RagService` returns an `AnswerResult` with `degraded=True`, a plain-language notice as the answer, the retrieved passages in `retrieved_sources`, the attempt records and an `all_providers_failed` error, preceded by an `error` event. A retrieval failure gives `retrieval_failed` and a notice (no model call); an unexpected exception in the generation path is reported as `internal` with the exception class only. An empty or over-long question (default cap 500 characters) raises a typed `InvalidQuestion` before any retrieval or LLM call. No retrieved passages means an abstention without calling the model.
- **Why (the problem it solves):** A research assistant whose search works but whose language-model provider is down should still show the passages: the user can read them. A stack trace in the UI helps nobody, and errors that carry exception text can leak paths or keys, so only class names and our own messages are surfaced.
- **Alternatives considered and why rejected:** Raise to the UI (every caller must re-implement the fallback); return an empty answer (indistinguishable from "no answer exists"); hide the failure behind a canned answer (dishonest).
- **Trade-offs / what it costs:** The caller must handle `degraded` and `partial` flags; a catch-all around the generation stage can hide a programming error, which is why it records the exception class and the result is flagged.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_service.py::test_every_provider_failing_returns_the_retrieved_passages_as_a_degraded_result_never_a_crash`, `::test_open_breakers_degrade_without_calling_any_provider`, `::test_a_retrieval_failure_is_a_typed_error_event_and_the_model_is_never_called`, `::test_an_unexpected_exception_in_the_generation_path_becomes_an_internal_error_not_a_crash`, `::test_a_bad_question_is_rejected_with_a_typed_error_before_any_retrieval_or_llm_call`, `::test_the_result_round_trips_through_json_and_contains_no_api_key`.
- **Likely interview questions and strong answers:**
  - *"What does the user see when the LLM is down?"* — "The passages that retrieval found, with a notice. The search part still works, so the product degrades instead of failing."
- **Honest limitations:** There is no queue or retry-later; no health endpoint; the degraded notice is English only.

### Why top_k=5 for the LLM context is a default, not a tuned value
- **What we did:** `rag_core/context.py::DEFAULT_MAX_CHUNKS = 5` (configurable as `generation.top_k`), with a comment saying it is a design default. `build_context` keeps relevance order, stops at the chunk limit or the token budget, never returns an empty context (an oversize first chunk is truncated, marked `[...]`), measures the budget with `rag.tokens.estimate_token_count` (a deliberately conservative WordPiece-style estimate that over-counts for the BPE tokenizers of the generators; each source also pays a fixed wrapper overhead) and returns the used chunk ids with labels S1..Sn.
- **Why (the problem it solves):** Five is a conventional starting point, not a measured optimum. What the evaluation actually showed (dev split, retrieval only, paper mode) is a trade-off with no single best k: the cleanliness of the retrieved set, measured as paragraph-level Evidence-F1, FELL as k grew, while recall rose (HitRate and Evidence-Recall). More chunks raise the chance that the evidence is present and also add distractors, prompt length and cost. Which k gives the best ANSWERS is an end-to-end question that retrieval metrics cannot answer, and that evaluation has not been done. I also did not tune it on the test split, which has been used once for the retrieval comparison and is spent.
- **Alternatives considered and why rejected:** Pick k from the retrieval metrics (they disagree: precision-like falls, recall-like rises); pick the largest k that fits the context window (maximises distractors and cost); tune on the test split (spent, and it would be selection on the reporting set).
- **Trade-offs / what it costs:** A default may be too small (missing evidence) or too large (distractors). The budget in tokens is a second limit so a few very long chunks cannot blow up the prompt.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_context.py` (order, labels, budget, oversize first chunk, never empty, `test_default_is_five_chunks_and_documented_as_a_design_default`); the dev observation is in the paper-mode dev runs under `runs/eval/` (Stage 2a), dev only and not published.
- **Likely interview questions and strong answers:**
  - *"Why five chunks?"* — "It is a default I chose, not a tuned value. On my dev retrieval runs, recall rose with k while Evidence-F1 fell, so retrieval metrics alone cannot pick it. The right k needs an answer-quality evaluation, and that is future work."
- **Honest limitations:** The token estimate is conservative, not exact for either generator; the dev observation is from a small dev split and a retrieval-only metric; with a different embedder or chunker the trade-off could move.

### One generation provider; Gemini only as an offline judge
- **What we did:** The demo path generates with Groq only (`generation.providers: ["groq"]`, model `openai/gpt-oss-120b`). Gemini is configured as the offline evaluation judge (`generation.judge`) and is not wired into `build_gateway` unless someone lists it in `providers`. The failover code stays (it is tested), but the product no longer depends on two vendors being healthy.
- **Why (the problem it solves):** A second provider in the request path doubles the keys, the failure modes, the privacy surface and the cost uncertainty, for a demo. Using a different model family as the judge also avoids the model grading its own answers. A live check before the change showed the model id I had configured (`llama-3.3-70b-versatile`) does not exist on this account: the failure was a clean 404 and the app degraded, but only the live check found it (`scripts/check_model_ids.py`).
- **Alternatives considered and why rejected:** Keep Groq to Gemini failover in the app (more moving parts, and mid-stream failover is already forbidden, so it only helps for failures before the first token); a single provider for both answering and judging (self-preference bias).
- **Trade-offs / what it costs:** A Groq outage means degraded mode (passages only), not an answer from another model.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_groq_only.py` (default gateway has one provider; a 500, a 404, a 401 and a missing key all degrade with the retrieved passages and without leaking the key; a 429 is retried; a broken stream is a mid-stream error, not a second provider); `tests/unit/test_rag_core_imports.py::test_build_gateway_builds_only_the_configured_providers_lazily_without_keys_or_network`; `scripts/smoke_generate.py` (live, prints PASS/FAIL checks, no numbers).
- **Likely interview questions and strong answers:**
  - *"Why not keep a fallback model?"* — "A fallback before the first token is cheap to keep in code, but in a demo it doubles the surface for little benefit. The degraded mode already guarantees the user sees the evidence."
  - *"Why a different model as judge?"* — "To avoid a model scoring its own output."
- **Honest limitations:** The judge is not used yet (that is a later phase); the Gemini judge needs a thinking budget or a larger output allowance because a thinking model can return empty text at a tiny output limit (observed in the live check).

### Prompt management: benefits and the risk
- **What we did:** The two answer prompts (`rag-answer-long`, `rag-answer-short`) live in Langfuse Prompt Management (chat prompts, label `production`) and are fetched with a short timeout and a TTL cache (`rag_core/prompt_store.py`). The templates in `rag_core/prompts.py` stay as the source of truth and the fallback. Seeding and comparison are `scripts/seed_prompts.py` (dry run by default, creates only what is missing, idempotent by hash) and `scripts/check_prompt_drift.py`. Every answer records the prompt name, version, source (`local`, `langfuse`, `local_fallback`) and the sha256 of the template; the cache key carries the same id.
- **Why (the problem it solves):** Prompt wording can then change without a deploy, each trace shows which version produced the answer, and a generation links to its prompt version in the Langfuse UI. The RISK is the mirror image: a prompt edited in a web UI bypasses code review and the test suite. So a fetched prompt is VALIDATED before use (exactly the variables `sources` and `question`, none in the system message, one system message, valid roles, plain messages, the abstention sentinel and (long prompt) the citation instruction present, a length cap) and an invalid, missing or unreachable prompt falls back to the local template, with the reason on the trace. Escaping stays in code and happens before the variables are filled in, so no prompt text can disable it.
- **Alternatives considered and why rejected:** Prompts only in code (no UI, no per-version linking, but safest; kept as the fallback); fetching without validation (a typo in the UI would reach users); blocking on Langfuse (an outage would take the answers down).
- **Trade-offs / what it costs:** One more dependency and a second place where the prompt can drift from the code (hence the drift check and the hash in the cache key); the validator only checks structure, it cannot judge whether an edited prompt is a good prompt.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_prompt_store.py` (every invalid shape is rejected and falls back; fetch errors fall back; pins; inert variables; `test_REAL_SDK_compile_agrees_with_ours_on_adversarial_values` compares our compile with the real SDK class offline); `tests/unit/test_rag_core_prompt_sync.py`; a mutation check (validation switched off) made 16 tests fail and was reverted; live: seeding created version 1 of both prompts, a second run created nothing and the drift check reported none.
- **Likely interview questions and strong answers:**
  - *"What if someone breaks the prompt in the UI?"* — "A structural validator rejects it and the local template is used; the trace records the fallback. What it cannot catch is a valid but worse prompt: that is what the evaluation and pinned versions are for."
  - *"Why keep the prompts in code too?"* — "They are the reviewed, tested source of truth and the fallback, and evaluation runs use the local or a pinned version so results are reproducible."
- **Honest limitations:** The fallback hides an outage from the user by design; it is visible only in traces. A pinned version is needed for reproducible evaluation (supported via `prompts.pin`, not yet used by a run).

### Tracing is optional and fails open
- **What we did:** `RagService` always wraps the tracer in `SafeTracer`: every tracer call is guarded, exceptions are swallowed and counted, and a request with no tracer, no keys, a sampled-out request or a request over the daily cap simply is not traced. The default tracer is a no-op that never imports the SDK. Spans are created explicitly (parent and child) instead of through ambient OpenTelemetry context, because the service is a generator that yields mid-request. The span tree is `rag.request` > `route`, `cache.hit` or `cache.miss`, `retrieve`, `context`, `generation` (linked to the prompt version), plus a `prompt.fallback` event when relevant. The root level is `WARNING` for a degraded request and `ERROR` for a failed one.
- **Why (the problem it solves):** Observability must not be able to take the product down or change an answer. Flushing is bounded (a helper thread with a timeout) so a slow Langfuse cannot stall a request.
- **Alternatives considered and why rejected:** The `@observe` decorator and ambient context (fragile across a generator that yields and across threads); no wrapper, trusting the SDK (one bug in a span attribute would become a user-facing error); synchronous flush per request (adds the network round trip to latency).
- **Trade-offs / what it costs:** A dropped trace is invisible except for the counters; sampling and the cap mean the dashboard is a sample, not a census.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_service_tracing.py::test_a_tracer_that_raises_on_every_call_leaves_events_and_the_result_unchanged` (normal, degraded, mid-stream and retrieval-failure scenarios compare the events and the result with an untraced run), `::test_invalid_input_with_a_broken_tracer_still_raises_the_typed_error_not_the_tracer_error`, `::test_an_aborted_consumer_still_ends_the_root_and_marks_it_aborted`; `tests/unit/test_rag_core_tracing.py`; a mutation check (the raw tracer without the wrapper) made 7 tests fail and was reverted; live: `scripts/smoke_trace.py` produced the documented tree for a normal request, a cache hit and a forced Groq failure.
- **Likely interview questions and strong answers:**
  - *"What happens if Langfuse is down?"* — "Nothing the user sees. Calls are guarded and the flush is bounded; the request is untraced."
  - *"Why manual spans?"* — "The pipeline is a generator; ambient context breaks when a generator yields to another context, so I pass the parent explicitly."
- **Honest limitations:** `LangfuseTracer` is tested against a fake client plus the live smoke, not against every SDK failure mode; with the SDK's default span filter, only spans from the Langfuse client are exported, which is what we use.

### What we send to Langfuse and what we deliberately do not
- **What we did:** A capture mode decides what leaves the process BEFORE any tracer is called: `masked` (default): the question and the answer truncated, with URLs, e-mail addresses and long digit runs redacted; sources as ids, section, rank and score only, no passage text and no compiled prompt; `full`: the whole question, answer, passages and compiled prompt (for a debugging session); `none`: no question or answer text. Key-like strings (Groq, Google, Langfuse and generic long tokens) are redacted in EVERY mode, and redaction happens before truncation so a cut can never split a secret. API keys are read only in `rag_core/env.py`, `gateway.py`, `langfuse_client.py` and the reader (a static test enforces this), and `.env` is read only through an allowlist of five names.
- **Why (the problem it solves):** Traces are a second copy of user input on a third-party server. The data here is public Qasper text, but the habit matters: the app will take questions from anyone, so the default sends the minimum and anything sensitive is opt-in.
- **Alternatives considered and why rejected:** Send everything (simplest, and a privacy problem the first time a user types something personal); rely on Langfuse-side masking (data has already left); no tracing of content at all (the traces would not help debugging).
- **Trade-offs / what it costs:** In masked mode a trace shows which chunks were used but not their text, so debugging a bad answer needs `full` mode or a local lookup by chunk id.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_tracing.py` (every key shape in every mode, truncation after redaction, masked sources carry no text, `none` carries no text); `tests/unit/test_rag_core_service_tracing.py::test_no_key_like_string_reaches_the_tracer_in_any_mode_even_from_a_provider_answer`; `tests/unit/test_rag_core_imports.py::test_api_keys_are_read_from_the_environment_only_and_only_where_expected`.
- **Likely interview questions and strong answers:**
  - *"Could a key end up in a trace?"* — "Not through the paths I control: keys are redacted in every capture mode and never printed or logged by the package (a test forbids print and logging). A key pasted into a question would be redacted by pattern; an unusual key format would not."
- **Honest limitations:** Redaction is pattern-based, so an unknown key format or a personal detail that does not look like an e-mail, URL or number would pass; `full` mode sends passage text.

### Score schema defined up front
- **What we did:** `rag_core/scores.py` fixes the score names, types and ranges before anything writes them: `user_feedback` (boolean, written by the thumbs buttons) and reserved numeric scores for the offline evaluation (`ragas_faithfulness`, `ragas_answer_relevancy`, `answer_f1`, `judge_agreement`). `submit_feedback` validates, uses a deterministic score id (`<trace id>-<name>`) so changing your mind updates the score instead of adding a second one, masks and truncates the comment, and never raises.
- **Why (the problem it solves):** Free-form score names drift (`feedback`, `thumbs`, `helpful`) and make dashboards and later joins with the evaluation impossible. A score is also a billable unit, so duplicates cost money.
- **Alternatives considered and why rejected:** Write scores ad hoc where needed; no validation (an out-of-range value would pollute averages).
- **Trade-offs / what it costs:** Adding a score means editing one table; reserved scores are defined but unused.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_observability.py` (score schema, range and type validation, deterministic id, masked comment, no trace id means nothing is sent, SDK failures return False).
- **Likely interview questions and strong answers:**
  - *"Why define scores you do not write yet?"* — "So the offline evaluation and the UI feedback land on the same names and types, and the dashboards can join them."
- **Honest limitations:** A feedback score exists only for requests that were traced (sampled in, under the cap); there is no per-user identity.

### Read side: status instead of exceptions
- **What we did:** `rag_core/observability_reader.py` turns the Langfuse Metrics API v2 into panels for the Observability tab. Every panel returns `Panel(status, data, as_of, message, sample)` with status `ok`, `no_data`, `no_keys` or `unavailable`, and `data` always has the same shape (an explicit empty structure when there is nothing), so the UI needs no `None` checks. One TTL cache covers every query, failures are cached briefly, and a local daily budget of queries stops the reader before the plan's own daily limit. `sample_data()` returns the same shapes with clearly labelled FAKE values for UI development.
- **Why (the problem it solves):** A dashboard that raises when the vendor is slow, rate limited or empty is worse than no dashboard. The free plan allows very few Metrics API requests per day, so caching is a requirement, not an optimisation.
- **Alternatives considered and why rejected:** Query on every page load (burns the daily allowance); compute the panels from our own logs (a second store to maintain); let exceptions reach the UI.
- **Trade-offs / what it costs:** Data can be up to the cache TTL old (each panel reports `as_of`); the panels are aggregates, not per-request drill-downs.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_observability.py` (every status, HTTP 429/401/403/500, exceptions and malformed bodies, TTL and error TTL with a fake clock, the daily budget and its UTC reset, sample shapes equal real shapes). The tests found two real bugs before any live run: the cache key contained the moving time window, so a repeated read never hit the cache and would have burned the daily allowance; and one panel was not guarded against an odd response shape. The live run then found a third that no fake could: the reader filtered on a column the API does not have (`statusMessage`), the failed query was swallowed and the dashboard showed zero degraded requests. It now uses the root observation's level, and a test pins every dimension and filter column to the list the API itself reported.
- **Likely interview questions and strong answers:**
  - *"How do you know the dashboard is right?"* — "I checked the field names against the live API and compared a panel with the three requests I had just made. The unit tests use a fake HTTP layer, so they prove behaviour, not that the vendor's field names are right; that is why the live smoke exists."
  - *"Why return a status instead of raising?"* — "The UI can render every state (loading, empty, no keys, unavailable) from one object."
- **Honest limitations:** A swallowed failure can still look like an empty panel: the message field must be shown by the UI; the aggregates depend on traces being sampled in; the cost panel stays at zero until real prices are configured.

### Free-tier unit budget: observations per request
- **What we did:** A traced request emits one trace and a small bounded number of observations (the tree above: at most eight, asserted by a test), plus one score on feedback. `tracing.sample_rate` and an in-memory `tracing.daily_request_cap` limit how many requests are traced at all; evaluation runs are not traced unless `tracing.trace_evaluation` is true; masked capture keeps payloads small.
- **Why (the problem it solves):** The free plan meters traces, observations and scores together per month, and a demo that is shared publicly can exhaust it in days. Running out stops the data, not the product, but the dashboard then lies by omission.
- **Alternatives considered and why rejected:** One observation per retrieved chunk or per stream chunk (richer, several times the cost); tracing everything and paying later; a persistent cap (a database for a cost guard).
- **Trade-offs / what it costs:** The cap is per process and per UTC day: a restart resets it. It is a cost guard, not an accounting system.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_service_tracing.py::test_a_normal_answer_has_the_documented_span_tree_with_one_root_and_at_most_eight_observations`; `tests/unit/test_rag_core_tracing.py` (sample rate, daily cap and its reset, a sampled-out request does not consume the cap); `docs/langfuse_notes.md` records the plan limits and where they come from.
- **Likely interview questions and strong answers:**
  - *"How do you keep tracing inside a free plan?"* — "A small fixed span tree, sampling, a daily cap, and no tracing of evaluation runs by default. I would raise the cap or move plans before I would add spans."
- **Honest limitations:** The plan limits are the vendor's and can change; the per-request unit estimate is from the span tree, not from the vendor's invoice.

### An isolated evaluation environment and a custom RAGAS judge

### Reasoning effort is a recorded parameter, not a default
- **What we did:** `generation.reasoning_effort` (`low`, `medium`, `high`, or none to omit it) is passed to Groq for `gpt-oss-120b`, validated when the gateway is built, recorded on every `AnswerResult` and trace, and part of the cache key. `completion_tokens` is kept exactly as the API reports it (a live probe showed it already INCLUDES the reasoning tokens); `reasoning_tokens` is stored separately and never added again. The output caps were raised (1,024 long, 512 short) because reasoning tokens count toward them and a 64-token cap would truncate short answers.
- **Why (the problem it solves):** Omitting the parameter behaved like `medium` in a live probe, i.e. the demo was running with an effort nobody had chosen. A parameter that changes the answers and the cost must be on the record and in the cache key, or two runs that differ in it look identical.
- **Alternatives considered and why rejected:** Leave it to the API default (an unrecorded, changeable behaviour); add `reasoning_tokens` to `completion_tokens` (double counting); keep the old caps (a reply cut off while reasoning looks like an empty answer).
- **Trade-offs / what it costs:** `low` is a demo default, not a tuned value; a lower effort may cost accuracy on hard questions.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_groq_only.py` (the effort is sent, recorded, validated and keyed; usage tokens are kept separately; reasoning text never enters the answer); a live probe made before the change (ad hoc, printed to the console and NOT saved as an artifact, so it is an observation and not evidence) showed the usage field semantics; the first saved evidence is the per-call usage in `runs/gen_dryrun/20261122T172032Z_quota_dry_run/dry_run.json` (reasoning tokens reported separately from completion tokens).
- **Likely interview questions and strong answers:**
  - *"What reasoning effort did you evaluate at?"* — "Low, recorded in every result and in the pre-registration. I did not tune it; evaluating medium and high would be a separate pre-registered comparison."
- **Honest limitations:** Groq's prices could not be read from its pages (client-rendered), so `generation.prices` stays empty and no cost is computed; a cost number would be an estimate, which the evidence rules forbid.

### Answer-F1 first, RAGAS second
- **What we did:** The generation evaluation's first metric is the official-style Answer-F1 (`eval/answer_metrics.py`): SQuAD normalisation, token F1, the MAXIMUM over the annotators' references, an abstention on an answerable question scored 0, table-only references skipped. Next to it: yes/no accuracy, abstention rate and citation validity, all pure functions with hand-built tests. RAGAS (faithfulness, answer relevancy) is computed afterwards, on the long answers only, and labelled EXPLORATORY.
- **Why (the problem it solves):** A deterministic metric with a published definition can be re-computed by anyone from the saved answers and gives the same number. An LLM judge cannot: its score depends on the judge model, its prompt, its thinking budget and the day. So the number that carries the claim should be the one that is reproducible, and the judge's opinion should be reported as context, not as the result.
- **Alternatives considered and why rejected:** RAGAS answer correctness as the headline (judge-dependent, and uncalibrated here); exact match (too harsh for abstractive answers: a right answer in other words scores 0); a mean over annotators instead of the max (the official definition takes the best match because annotators phrase the same answer differently; a mean punishes a correct answer for not matching a different annotator).
- **Trade-offs / what it costs:** F1 rewards word overlap, so a correct abstractive answer in other words scores low, and a long wrong answer that happens to contain the reference words scores high. Two documented departures from the official evaluator: Unicode punctuation is stripped too (models emit typographic quotes and dashes), and extractive references are stored joined by a space (identical after normalisation, tested).
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_answer_metrics.py` (32 hand-built cases: normalisation edge cases, hand-computed F1 values, max over references, ties, table-only references skipped, yes/no, abstention, citation validity, clustered intervals). A mutation check (the mean instead of the max in `answer_f1`) made 2 tests fail and was reverted.
- **Likely interview questions and strong answers:**
  - *"Why is the primary metric not an LLM-judged one?"* — "Because I can reproduce it. The judge is a second model with its own settings and I have not calibrated it against human labels; I report it, but I do not hang the conclusion on it."
  - *"Why max over references?"* — "That is the official Qasper definition and the reason is that annotators differ in phrasing; a mean would penalise a correct answer for not matching a different annotator."
- **Honest limitations:** n=40 on the dev split and one arm; word overlap is a blunt instrument; the numbers are exploratory and not in `CLAIMS_LOG` as results.

### A judge from a different model family, pinned, and NOT calibrated: what that means for the claims
- **What we did:** Faithfulness and answer relevancy are scored by Gemini `gemini-2.5-flash` while the answers come from Groq `gpt-oss-120b`: a different family, temperature 0, a recorded thinking budget (1,024) and output limit (4,096), the `v1beta` API version, ragas 0.4.4, answer-relevancy `strictness=1`, and every judge call cached on disk under a key that includes all of them plus the metric name. The scoring run's `config.json` records all of it. The judge is a custom adapter on RAGAS's documented LLM interface, because RAGAS's own Google path could not set or even confirm a thinking budget.
- **Why (the problem it solves):** A model grading its own family's output tends to favour it; temperature 0 and a recorded budget are what make "the judge" one definite thing rather than a drifting one. The cache key is what stops a verdict from one judge, metric or ragas version being served for another.
- **Alternatives considered and why rejected:** The same model as judge (self-preference); ragas's built-in Google path (no thinking budget, no usage, an uncontrolled cache key); an unpinned "latest" judge (the same run could not be repeated).
- **Trade-offs / what it costs:** The judge is NOT calibrated: no human labels exist. So a faithfulness score is the judge's opinion, and an agreement with humans is unknown, may differ by answer type, and may be poor on scientific text because RAGAS's prompts are general-purpose. Consequence for the claims: every RAGAS number is labelled EXPLORATORY and "uncalibrated judge" wherever it appears, none goes into the README, and the calibration (40 answers, human labels, agreement and Cohen's kappa) was cut from this phase and is the first thing to add before any RAGAS number is quoted as a result.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_judge_and_ragas_runner.py` (the cache key changes with the judge model, thinking budget, output limit, API version, metric, ragas version, prompt and response schema; only valid replies are cached; the per-minute 429 is waited out; a per-day 429 or the call budget stops the session cleanly); `tests/unit/test_ragas_adapter.py` (against the REAL ragas classes with a fake judge, in `venv_eval`). A mutation check (a cache key that ignores the metric name) made 3 tests fail and was reverted.
- **Likely interview questions and strong answers:**
  - *"How much do you trust the faithfulness score?"* — "As an indicator, not as a measurement. I pinned the judge and cached its calls so it is repeatable, but I have not checked it against human labels, so I do not know how often it is wrong."
  - *"Why Gemini for a Groq-generated answer?"* — "A different family avoids the self-preference problem; it does not remove the need to calibrate."

### Quota-aware evaluation: caching and resumable runs
- **What we did:** The generation runner counts the tokens of every response's `usage` in a ledger (a rolling 24 hours), refuses to start a call that would exceed `--daily-token-budget` (default 180,000, below the generator's documented 200,000 tokens/day), and exits cleanly with "quota exhausted, resume later" (exit code 3) when the budget is reached or the provider answers HTTP 429. Every finished generation is cached on disk (key: model, reasoning effort, prompt name, version and hash, arm, mode, question, context hash, caps, temperature, top_k) and every judge call is cached too, so running the same command again costs nothing for what is done. Each session writes a run folder and says tokens used, questions done and what remains. A pacer keeps calls under the per-minute limits.
- **Why (the problem it solves):** The free tiers decide what is possible (a Groq daily token limit, a Gemini limit of a few requests a minute). An evaluation that cannot be interrupted and continued either loses work at the first 429 or tempts you to shrink the sample until it fits. The dry run measured the cost first; this is the mechanism that makes a multi-session run safe.
- **Alternatives considered and why rejected:** No governor and rely on the 429 (the daily allowance is spent before you know); a calendar-day counter (the provider's window is not documented as a calendar day, so a rolling window is the conservative reading); caching only the final scores (a crash would repeat all the paid calls).
- **Trade-offs / what it costs:** The governor counts only what this project sent (Groq's headers give no tokens/day), so tokens spent elsewhere in the window have to be declared (`--already-used-tokens`); a cache key that includes the context hash re-pays if retrieval ever returns different chunks (not observed in the runs so far, but HNSW search is not guaranteed bit-reproducible across processes).
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_run_generation_eval.py` (the budget stops the session BEFORE the call that would exceed it; repeated sessions finish the sample with every (question, mode) generated exactly once; a 429 caches nothing for the failed call; a fully cached re-run makes no call; a changed reasoning effort or context is a miss) and `tests/unit/test_judge_and_ragas_runner.py` (a judge quota stop, then a resume, pays for each distinct judge call exactly once). The sliding-window pacer and the plan arithmetic are in `eval/quota_plan.py` with tests in `tests/unit/test_gen_arms_and_quota.py`.
- **Likely interview questions and strong answers:**
  - *"What happens when you hit the rate limit mid-run?"* — "The session stops cleanly, the finished work is already on disk, and running the same command resumes. The failed call is never cached."
- **Honest limitations:** The ledger is local: a second process sharing the key would not be seen; the Gemini per-day limit is not published, so it is handled when it is hit rather than planned.

### Why production traces are not RAGAS-scored
- **What we did:** The RAGAS scoring reads a generation EVALUATION run (answers plus the exact passages sent to the generator, stored in the run folder), never Langfuse traces. In the demo, traces are captured in `masked` mode by default: the question and answer are truncated and redacted, and the sources are recorded as chunk ids, section, rank and score only, with no passage text.
- **Why (the problem it solves):** Faithfulness and the context metrics need the passages the model saw. A masked trace deliberately does not hold them, so a judge reading it would score the answer against nothing, and a judge reading a `full` trace would mean copying user questions and passage text to a second third party (the judge's provider) with no consent. The evaluation set is public Qasper text and public questions, so it can be sent; a production trace is a user's input.
- **Alternatives considered and why rejected:** Scoring production traces in `full` capture (a privacy cost and a data-flow the users did not agree to); reconstructing the passages from chunk ids at scoring time (possible locally, but still sends user text to the judge); sampling live traffic for scoring (the same problem, plus the free-tier quota).
- **Trade-offs / what it costs:** There is no online quality signal from production: only latency, errors, cache hits and the thumbs feedback. Quality is measured offline on a fixed set.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_tracing.py` and `tests/unit/test_rag_core_service_tracing.py` (masked mode records no passage text and no compiled prompt); `eval/run_ragas.py` only accepts a generation run folder (a test refuses a folder that is not one and a folder whose checksums do not match).
- **Likely interview questions and strong answers:**
  - *"Why not monitor answer quality in production with RAGAS?"* — "Because the privacy default means the traces do not hold the passages, and sending real user text to another vendor for scoring is a decision I would want consent for. The thumbs feedback is the online signal; quality is measured offline."
- **Honest limitations:** A user-facing regression in answer quality would not be caught by the dashboards until feedback accumulates.

### The citation parser read `【S1】` as "no citations"
- **What we did:** The first live generation at `reasoning_effort="low"` produced answers that cite as `【S1】` (lenticular brackets), where the earlier default behaviour used `[S1]`. The citation parser only recognised ASCII brackets, so valid citations were reported as none. The parser (`rag_core/citations.py`) and the metric-side marker stripper now accept `[S1]`, `【S1】` and `［S1］`, with lists such as `[S1, S2]`; malformed forms (`[s1]`, `[S 1]`, `【S】`) stay malformed, and markers inside code are still ignored. The generation cache schema was bumped so entries that stored "no citations" are never read (the old files are left in place).
- **Why (the problem it solves):** A silent undercount: the answers were fine, the product would have shown no citations, and the citation-validity metric would have reported a failure of the model that was really a failure of the parser. Found only because the first live answers were read, not just scored.
- **Alternatives considered and why rejected:** Rewriting the model's text to ASCII brackets (changes what the model said; the parser should read, not edit); tightening the prompt to demand ASCII (a prompt change, which would bump `PROMPT_VERSION` and invalidate the pinned evaluation; the parser is the cheaper and more robust fix); ignoring it (the metric would be wrong).
- **Trade-offs / what it costs:** The UI shows the model's own brackets as written; the set of accepted bracket forms is a list that a different model may extend.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_citations.py` (lenticular and full-width forms, lists, mixed ASCII and lenticular, malformed forms, code, and a service-level test with `【S1】【S9】` giving one valid and one invalid citation); `tests/unit/test_answer_metrics.py` (the stripper).
- **Likely interview questions and strong answers:**
  - *"How did you find it?"* — "I read the first answers instead of only looking at the summary table. The table said zero citations; the text had them."
- **Honest limitations:** The effect of the effort level on citation style was seen, not isolated: it may also depend on the question. Whether `low` reduces how often the model cites at all is a measurement for the evaluation to report, not something this fix addresses.

### Abuse protection for a public demo
- **What we did:** `app/guards.py` (pure, injectable clocks), all limits in `config.yaml` under `app.*`: an optional access code (`APP_ACCESS_CODE`, compared with `hmac.compare_digest` on bytes, a lockout after repeated wrong codes, the secret never in any repr, message or session value; open "demo mode" with a note when unset); a per-session rate limit and per-session cap; the question length cap reused from `rag_core`; and a process-wide daily request cap shared by all sessions, beyond which NO LLM call is made and the retrieved passages are shown (`RagService.passages_only`). The daily unit is given back when no model call happened (cache hit, small talk, a failed call).
- **Why (the problem it solves):** A public page in front of a free-tier key can be drained by anyone. The binding constraint is the provider's daily token limit, so the cap is on requests (a proxy for tokens: long answers cost more than short ones, which is why the default is set well below the budget rather than at it).
- **Alternatives considered and why rejected:** A per-IP limit (Streamlit does not expose a trustworthy client address); a captcha (a third-party call and a dependency for a local demo); no limit (one loop empties the day's quota and takes the demo down for the owner).
- **Trade-offs / what it costs:** The daily cap is in memory, so a restart resets it, and it is per process, not per day on the provider's clock. A shared access code is a gate, not user authentication.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_app_guards.py` (fake clocks, the lockout, the secret never rendered), `tests/unit/test_app_ui.py` (a wrong code blocks, the right code opens; the cap is shared by all sessions; a refused question is not counted). Mutation check: removing the daily-cap branch in `app/ui_chat.py::submit` made 4 tests fail (reverted).
- **Likely interview questions and strong answers:**
  - *"What stops someone from burning your quota?"* — "A shared daily cap that degrades to retrieval-only instead of calling the model, a per-session limit, an access code, and a question length cap. The failure mode of the cap is the demo getting less useful, never a bill or a crash."
- **Honest limitations:** No protection against a distributed or determined attacker, no persistence of the counters across restarts, and the cap counts requests, not tokens.

### Rendering citations from the parsed result
- **What we did:** The text shown to the user is built from the validated `AnswerResult`, not from the raw stream: `【S1】` and `［S1］` are normalised to `[S1]`, valid markers are shown bold and each points at its source card (a cited card says so), invalid markers named by the parsed result are dropped and noted quietly in a caption, and `$` is escaped so a price is not read as LaTeX. While tokens stream, a normaliser that holds back a partial marker keeps half-markers off the screen.
- **Why (the problem it solves):** The model cites as `【S1】` at low reasoning effort (the earlier parser bug), so "what the model wrote" and "what is a citation" differ. The parsed result is the one definition of a citation; showing it keeps the UI, the evaluation metric and the cards consistent.
- **Alternatives considered and why rejected:** Rendering the raw text (shows brackets the validator does not recognise); regex-fixing in the UI independently of `rag_core/citations.py` (two definitions that drift); linking markers to anchors (Streamlit has no stable in-page anchor for expanders).

AppTest could not see this because it does not render Markdown; it was found by using the real app in a browser, and is now fixed and covered by a test that renders the markup with a Markdown parser (`test_a_marker_touching_bold_text_...` in `tests/unit/test_app_support.py`).
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_app_support.py` (normalisation, styling, partial markers, the asterisk case), `tests/unit/test_app_ui.py` (a `【S1】` answer renders `[S1]`, an invalid marker is flagged, markers match the cards).
- **Likely interview questions and strong answers:**
  - *"Does a bold [S1] mean the claim is supported?"* — "No. It means the model pointed at a passage that was really in its context. Whether the passage supports the claim is what faithfulness evaluation is for, and the page says so under every answer."

### Self-check screen instead of stack traces
- **What we did:** `app/bootstrap.py::build_resources` never raises: it runs named checks (index directory from `ADVRAG_INDEX_DIR`, else `CHROMA_LOCAL_PATH`; FTS5 available; the store and the lexical index open; vector count equals lexical count; chunk count equals the latest ingest manifest; the embedding model is in the local cache; an embedder warm-up) and returns a `SelfCheck`. A failed fatal check shows an error screen that lists the checks with a "Check again" button and nothing else; a missing Groq or Langfuse key is a warning (the app still shows passages; Observability shows `no_keys`). Keys are checked for presence (booleans), never shown. A failed bootstrap is not cached (`validate=` on `st.cache_resource`), so fixing the cause and pressing the button works without a restart. Each tab is wrapped so an unexpected error in one shows its class name, not a trace, and does not take down the others.
- **Why (the problem it solves):** The common failures (wrong path, a stale index, a missing model) are configuration, and a stack trace tells a visitor nothing and may leak paths. A named failed check tells the owner exactly what to fix.
- **Alternatives considered and why rejected:** Let Streamlit show the exception (leaks internals); fail silently with an empty answer (the worst case for a RAG app); make key checks fatal (the passages-only view is still useful and tests the retrieval half).
- **Trade-offs / what it costs:** The chunk-count-versus-manifest check refuses an index that was changed without a new manifest, which is intended but means a deliberate re-ingest also needs its manifest.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_app_support.py` (each check failing in turn, never raising), `tests/unit/test_app_ui.py` (a failed self-check shows the error screen and no tabs; a failed bootstrap is retried).
- **Likely interview questions and strong answers:**
  - *"What happens if the index is missing?"* — "The app starts, runs the self-check, and shows which check failed. It never serves answers from a store it could not verify."
- **Honest limitations:** The checks prove the store is consistent with its manifest, not that its content is good; the key check proves presence, not validity (an invalid key shows up as a degraded answer).

### Week 1, Step 3a (N-06): a reply that spent its whole budget on reasoning is not a provider outage
- **What we did:** Test-first. `rag_core/gateway.py::LLMGateway.stream` used to turn any stream without visible text into `ProviderError("other", EmptyResponse)`, and `"other"` is in `BREAKER_KINDS`, so three questions the model "thought about" until `finish_reason="length"` opened the Groq breaker for everybody. Now: (1) `finish_reason == "length"` with no text is `ProviderError("length", error_class="LengthWithoutText")`; `"length"` is neither a breaker kind nor retryable, so `_count_failure` only releases the breaker. (2) It is retried once on the same provider with `max_output_tokens x 2` (`LENGTH_RETRY_FACTOR`), capped at `LENGTH_RETRY_MAX_OUTPUT_TOKENS = 4096`, with no backoff sleep, and not retried when the cap is already at the ceiling. (3) When every provider failed only with length stops, the gateway raises the new `rag_core/errors.py::AnswerTooLong(attempts)`; if any provider failed for another reason it is still `AllProvidersFailed`, and a length failure still lets the next provider answer. (4) `rag_core/service.py` maps `AnswerTooLong` to `degraded=True`, `TOO_LONG_MESSAGE`, an `ErrorInfo(code="answer_too_long")`, keeps the retrieved passages, never caches it, and yields `error` then `done`. The Streamlit UI already renders `degraded` as a warning, so no UI change. Note: the prompt asked for "higher cap or reasoning_effort=low"; the reasoning effort is a provider constructor setting (default already `low`), so only the cap is raised per call.
- **Why (the problem it solves):** One verbose-reasoning question class could take the only provider out of service for 30 s for every user, and the user saw "service unavailable" for a question-level problem.
- **Alternatives considered and why rejected:** Counting length stops as breaker failures with a higher threshold (still blames the provider); retrying with `reasoning_effort` changed per call (needs a new provider call signature, a wider change); an unbounded cap increase (cost).
- **Trade-offs / what it costs:** A length stop can now cost up to two calls (the second with twice the tokens) before the user sees the message. The 4096 ceiling is a constant in the gateway, not in `config.yaml`.
- **Evidence it works (test or measurement, with file path):** 6 new tests in `tests/unit/test_rag_core_gateway.py` (5) and `tests/unit/test_rag_core_service.py` (1). ### Week 1, Step 3c (N-13): a failed Langfuse prompt fetch is remembered for 60 s
- **What we did:** Test-first. `rag_core/prompt_store.py::LangfusePromptStore._resolve` fetched the prompt on every request; when Langfuse was slow or down every request waited up to `fetch_timeout_seconds` (2 s) before falling back to the local template. Now a failed fetch (an exception, or the SDK's `is_fallback` object) is remembered per prompt name for `prompts.failure_cache_seconds` (new, 60 in `config.yaml` and `rag_core/config.py::PromptsConfig`; 0 turns it off): during that time `resolve` returns the local fallback with the same `fallback_reason` and without calling `get_prompt`. After the period the next request tries again; a success is not remembered. An invalid prompt and a missing key are deliberately NOT negative-cached (the SDK's own TTL cache already makes a repeated fetch cheap, and a corrected prompt in the UI must be picked up). The clock is injectable (`clock=`, default `time.monotonic`), the dict is guarded by a lock.
- **Why (the problem it solves):** During a Langfuse outage the first token of every answer was delayed by up to 2 s for every user, although the fallback was already known to be the answer.
- **Alternatives considered and why rejected:** A global (not per-name) memory (one outage flag: simpler, but one slow name would hide a healthy one); a circuit breaker class (more states than a 60 s memory needs); raising the SDK `cache_ttl_seconds` (the SDK does not cache failures).
- **Trade-offs / what it costs:** After Langfuse recovers, up to 60 s more of local prompts (they are the same text unless someone edited the prompt in the UI; the cache key carries the template hash, so the two never mix). With two prompt names, an outage costs one timeout per name per minute, not zero.
- **Evidence it works (test or measurement, with file path):** 5 new tests in `tests/unit/test_rag_core_prompt_store.py` using the fake client and `FakeClock` (burst of 10 requests = 1 fetch; 59 s no retry, 61 s retry; recovery after the period and success clears the memory; SDK-fallback object remembered; per-name memory; invalid prompt not remembered; 0 = off; default 60 equals `config.yaml`). ### Week 1, Step 3e (N-15): the total deadline is checked on every streamed delta
- **What we did:** Test-first. `LLMGateway.stream` checked `deadline_s` (90 s) only BETWEEN attempts, so a provider that kept dripping tokens (or empty reasoning deltas) could hold the request thread far past it. Now every `Delta` is checked against the monotonic start of the request: past the deadline, a `ProviderError("timeout", error_class="DeadlineExceeded")` is raised inside the existing handler, so the existing rules apply: text already yielded -> `MidStreamError(partial)` (no retry, no failover); nothing yielded yet -> the attempt fails and the request ends in `AllProvidersFailed` (the next attempt/provider sees the deadline and is skipped). A `DeadlineExceeded` is never retried with a backoff sleep. The provider's generator is now closed in a `finally` (`stream.close()`), which also releases the connection when the consumer stops early; `provider.stream(...)` is still called inside the `try`, so a provider that raises on call is still classified. The late delta is not yielded.
- **Why (the problem it solves):** The deadline was a promise the code could not keep: a slow-drip stream could occupy a Streamlit worker thread indefinitely and the per-call `timeout_s` only bounds silence, not a steady trickle.
- **Alternatives considered and why rejected:** A watchdog thread that cancels the call (a thread per request and a cancellation race for a check that costs one comparison per delta); lowering `timeout_s` (it bounds a single read, not the total); checking only visible-text deltas (reasoning-only deltas could still hold the thread).
- **Trade-offs / what it costs:** The check runs when a delta ARRIVES: a provider that goes completely silent is bounded by the SDK's per-call `timeout_s` (30 s), not by this check. A deadline stop counts as a `timeout` for the breaker (a provider that drips for 90 s is slow). The deadline constant is unchanged (90 s, not tuned).
- **Evidence it works (test or measurement, with file path):** 4 new tests in `tests/unit/test_rag_core_gateway.py` with a `SlowDrip` provider on the `FakeClock` (4 s per delta, `deadline_s=10`): the third delta ends the stream with `MidStreamError(partial="ab")`, `DeadlineExceeded`, the provider generator closed, no second provider, no backoff sleep; reasoning-only deltas -> `AllProvidersFailed` after one call with no sleep; a 9 s stream under a 10 s deadline is untouched; the deadline counts from the start of the request, including an earlier provider's backoff. RED before the fix: 3 failed, 1 passed (the regression guard). After: the whole gateway file **75 passed**. Smoke: `import rag_core, app` and the real config OK. Per the owner's testing policy no full run and no revert check now; the full suite runs in Step 4.
- **Likely interview questions and strong answers:**
  - *"How do you bound the total time of a streaming call?"* — "A monotonic deadline from the start of the request, checked on every chunk; on expiry I close the provider's stream and end with a typed partial error. The per-call timeout only bounds silence between bytes."
  - *"Why not retry after a deadline?"* — "The budget is spent; a retry or a sleep would only exceed it further."
- **Honest limitations:** A fully silent provider is only bounded by the SDK timeout. The 90 s value is a design default. Tested with a fake provider and fake clock only (no live Groq call).

### Long answers as schema-constrained structured output (claims with verified quote spans) instead of regex-parsed prose
- **What we did:** The long answer is now requested with a per-request JSON response schema (`rag_core/claims.py::answer_schema`, schema `claims-1`, Gemini `response_json_schema`): `status` (`answered` | `insufficient_context`) and `claims`, each `{text, citations: [{source, quote}]}`, where `source` is an enum of exactly the labels that were sent. The code checks each label against those sources and locates each quote word for word in its source (`locate_quote`: undo the prompt's HTML escaping, collapse whitespace, case-sensitive, at least 3 words), storing `start`/`end` offsets and `verified` on `SpanCitation` (`AnswerResult.claims`). `answer` is rendered by the code from the claims. While streaming, `StreamRenderer` parses the partial JSON (`pydantic_core.from_json(allow_partial="trailing-strings")`) and shows only claim text: never the JSON, never an abstention, and the display only grows. A reply that is not a structured answer is `invalid_output` (degraded, the passages are shown); JSON cut off by the output limit keeps the claims that arrived and is `partial`/`truncated`. The regex `[S#]` parser was deleted. The short answer is unchanged: plain text with the `INSUFFICIENT_CONTEXT` sentinel. The long prompt (`PROMPT_VERSION` `2026-11-27.1`) and its validator were changed together, so a Langfuse copy of the old prompt is refused. Evaluation rows carry `claims` and a new EXPLORATORY `QuoteVerified` metric, and the generation cache schema moved to 3. The UI shows each quote on its source card, marked found or NOT found. The gateway and `Provider.stream` take an optional `response_schema`.
- **Why (the problem it solves):** Parsing citations out of free text was fragile. The model was seen writing `【S1】`, which needed a special case, and a marker said only which passage the model pointed at, never which words. With constrained decoding the structure cannot drift, invalid source ids cannot be produced by a schema-following model, and every citation can be checked mechanically against a span of the passage.
- **Alternatives considered and why rejected:** (1) Keep the regex as a fallback for non-JSON replies: rejected, because it would keep the fragile path alive; a non-conforming reply is now an explicit `invalid_output` instead. (2) Ask the model for character offsets: models count characters badly; a verbatim quote plus code-side location gives exact offsets. (3) Fuzzy quote matching: rejected for now, because "found" must mean found. (4) No streaming for structured answers: rejected, because partial-JSON parsing keeps the streamed UX.
- **Trade-offs / what it costs:** JSON with quotes uses more output tokens than prose, and the 1,024-token cap was not re-tuned, so truncation is more likely (it is reported, not hidden). Claims are joined into one paragraph, so the model's own formatting (bullets) is lost. `MIN_QUOTE_WORDS = 3` is a design default. A paraphrased quote counts as not verified even when the claim is true. Until the owner re-seeds Langfuse, the app logs a `prompt.fallback` event on every long answer.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_rag_core_claims.py` (schema shape, quote location including a Hypothesis property over random word runs and separators, complete/partial/malformed parsing, streaming prefix property for chunk sizes 1-1000) and the migrated service, API, UI, injection, tracing and evaluation tests. Fast suite: 1418 passed, 65 skipped (baseline before the change: 1399 passed, 63 skipped). No live generation was run, so the model's real compliance with the schema is NOT measured.
- **Likely interview questions and strong answers:**
  - *"How do you know a citation is real?"* — "I don't parse it out of prose any more. The model fills a JSON schema whose source field can only be one of the passages I sent, and it has to copy a quote. My code then finds that quote in that passage and records the character span. 'Verified' means the words are really there. Whether they support the claim is a separate question, which is what faithfulness evaluation is for."
  - *"What happens if the model ignores the schema?"* — "It's reported as invalid output and the user gets the retrieved passages, never a half-parsed answer. If the JSON is cut off, the claims that arrived are kept and the answer is marked incomplete."
- **Honest limitations:** Not measured against the real model. The schema enum relies on the provider's constrained decoding: the code still validates, but the share of non-conforming replies is unknown. Streaming does not show markers until a claim is closed.

Extended the freeze/ledger idea for this set: a separate freeze (`eval/heldout_freeze.json`, not created) pins the data hash, arms, `top_k`, `candidate_k`, code fingerprint and pre-registration hash; `open_heldout` checks all of them, refuses any second opening (ledger line or `OPENED.json` marker, exclusive create), and records the opening before returning the path. Both evaluation runners now refuse the data or a byte-identical copy as an input.
- **Why (the problem it solves):** The existing "test" split is a slice of the official DEV papers and has been run once, so there was no unused held-out data. The official test split was untouched but not secured.
- **Alternatives considered and why rejected:** (1) Keeping it in the repo: it could be committed, read by tooling or picked up by a glob. (2) Reusing `eval/test_freeze.json` / `test_ledger.jsonl`: they belong to the old split, must not be edited, and the old ledger records openings without refusing a second one. (3) The HuggingFace `datasets` loader: not a pinned dependency, and it parses the data into a cache. (4) Encrypting the files: key handling for little gain on a one-person machine.
- **Trade-offs / what it costs:** The freeze pins the code fingerprint, so any `.py`/`.yaml` change after freezing blocks the opening. The first download is trusted (no publisher checksum was found), so the pinned hashes prove "unchanged since 2026-11-27", not authenticity beyond TLS from the official URL. Certificate verification uses system roots plus `certifi` (this Python had no system roots).
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_heldout.py` (fake archive: one download, read-only storage, refused suspicious archives, tamper detection, every freeze mismatch, exactly one opening, runner refusal, no other module names the data). The real fetch ran once; a second run reported "already secured" and `status` showed not frozen, not opened. A byte search of the stored test file found 0 of the 200 corpus paper ids (control: all 200 found in `corpus.json`); nothing was parsed or displayed (printed output, no saved run).
- **Likely interview questions and strong answers:** *"How do you know you didn't tune on the test set?"* — "It sits outside the repo with its hash committed. One function can hand it to an evaluation, only after a freeze of arms, code and pre-registration, and only once. It's a procedural guard, not a vault, but breaking it would show in the committed ledger."
- **Honest limitations:** A guard against accidents, not against someone with file access. One copy on one machine (re-fetching elsewhere accepts only identical bytes, so it depends on the URL staying up and unchanged). No runner consumes the set yet.

### Docker: public-index CPU build and compose for the API and the UI
- **What we did:** Rewrote the `Dockerfile`: no BuildKit pip secret; locked packages from public PyPI; `torch` installed first from PyTorch's public CPU wheel index; the build fails on `pip check`, a CUDA torch or any NVIDIA package; dev tools left out; non-root user. Added `compose.yaml` (services `api` and `ui` from one image, one-shot `ingest` under the `tools` profile, a named data volume, the HuggingFace cache bind-mounted read-only, loopback-only ports, only named variables passed). `.dockerignore` now also excludes `.venv/`.
- **Why (the problem it solves):** The old Dockerfile had never been built, required a private pip configuration and installed the CUDA torch build by default.
- **Alternatives considered and why rejected:** (1) PyPI's default torch wheel: CUDA on Linux x86_64. (2) `env_file: .env`: would pass every variable in `.env`, including unused cloud credentials. (3) Baking models or the index into the image: large, and models are never downloaded by the app. (4) Ingesting automatically on `up`: minutes of hidden work and a writer racing the API.
- **Trade-offs / what it costs:** One extra command before the first `up` (ingest, about 7 minutes in the Docker VM here). A second package index besides PyPI. The lock was compiled on Windows, so Linux-only `uvloop` (and the base image's `pip`) are not pinned by it. The image is about 3 GB.
- **Evidence it works (test or measurement, with file path):** `tests/unit/test_docker_files.py` (static). By hand on 2026-11-27, linux/arm64 (printed output, no saved run): image built; torch `2.15.0+cpu`, no NVIDIA package; ingest verified 7255 chunks with store/lexical parity; `compose up --wait` made both services healthy; `/v1/ready` true; `/v1/retrieve` returned 5 passages; `/v1/answer` without a key degraded to passages; the UI script ran in the container with no exception (Streamlit AppTest, not a browser).
- **Likely interview questions and strong answers:** *"Why isn't the model in the image?"* — "Images should carry code and pinned packages. Models are large, pinned by revision and mounted read-only, so the container can't download or change them."
- **Honest limitations:** No live Gemini or Langfuse call and no reranking in a container. UI not looked at in a real browser. No CI build.
